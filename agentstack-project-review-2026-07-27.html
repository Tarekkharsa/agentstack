The one-paragraph verdict

Ship-blocking problems are not in the engine — they are at the two ends of the funnel. At the front, the product's own declared primary surface (t3code) is a private fork with zero presence on the website, and the CLI's distribution is a stale Homebrew template pinned five minor versions back with no upgrade path. At the back, every user-validation gate in TODO.md Stages 1–3 is unchecked, so the "under five minutes" claim rests entirely on the author's own runs.

Between those ends sits one real safety defect (C1) and a cluster of coherence bugs that make a well-built tool feel unfinished within ninety seconds of the happy path ending.

01

What the project is

Read before judged: README.md, STRATEGY.md (816 lines), TODO.md (805 lines), CLAUDE.md, CONTRIBUTING.md, docs/design/launch-plan.md, the twenty-page docs site, and the crate tree — then the binary itself, driven end to end.

The vision, as the repo states it

"Define your agent setup once. Use it across every coding CLI." A vendor-neutral environment manager for AI coding tools: one portable manifest is the source of truth, and every CLI's native config is compiled output.

Two interfaces, one product

t3code is declared the primary graphical experience and launch channel; the CLI is the source of authority and automation contract. The old embedded dashboard was deliberately retired.

The problem it attacks

  • The same MCP server hand-copied into 4–6 incompatible config formats
  • Global config leaking into projects that do not need it
  • Task switching means editing shared files and remembering how to undo it
  • A teammate cannot reproduce your working setup
  • Repo-supplied config can execute code or receive secrets before you understand it

The first four are felt daily. The last is the one nobody else is solving — and the reason this project is more than a config linter.

The intended workflow, and where the seams are

install→ init→ review import→ apply --write→ doctor ┊ then ┊ create-profile→ session start→ session end→ doctor (5 warnings)

Green = verified smooth in this review. Amber = works but confuses. Red = hard stop for a first-time user (H1). The break is not in the acquisition journey — it is in the retention journey, exactly the one STRATEGY.md calls "the primary recurring-use feature".

02

Product review

Is this worth building, is the value obvious, and is the feature set coherent?

Yes — this is a real problem

I verified the premise on this machine: six agent CLIs on PATH, each with a different config format and location (~/.claude.json, ~/.codex/config.toml, ~/.gemini/settings.json, ~/.copilot/mcp-config.json, ~/.config/opencode/opencode.json). The duplication is not hypothetical, and it is getting worse every quarter, not better.

The bet that no vendor will build a neutral lifecycle manager for its competitors is sound and is the durable differentiator.

But the value proposition is not obvious enough

"One agent setup. Every coding CLI." is a good line. The problem is what follows it: the landing page's next move is a four-card problem list and a six-step ladder — an argument, where a first-time visitor needs a demonstration.

The one asset that proves the claim in eight seconds — docs/demos/first-value.gif — is roughly 2,400px down the page. M6

The killer features

1. doctor

The single best thing in the product. ~110 finding templates, every error carrying a ↳ with a real command, informational notes visually demoted, unused sections hidden by default, and one "start with:" triage line at the bottom.

0 error(s), 5 warning(s), 2 note(s).
  start with: agentstack apply --write

Most tools in this space cannot tell you why your MCP server does not load. This one names the file, the key path, and the fix.

2. explain <name>

Asks and answers the question every MCP user actually has: what is this thing, where did it come from, what does it run, what secrets does it touch, and which files will it land in? — in one screen, before you rely on it.

Undersold everywhere. It is not in the curated help list, not in the README, and not on the landing page.

3. Reversibility

Every material write is recorded, previewed, and undoable — with the demo asserting byte-for-byte restoration. uninstall previews the complete managed set and states plainly that it never touches your manifest.

This is what earns permission to write into six config files. It is the second-strongest asset and is also undersold.

The core product criticism

The feature set is cohesive on paper and incoherent in practice, because it was built in strategy order rather than journey order.

The manifest→render→diagnose→undo spine is genuinely one product. But bolted to that spine are a Boa JavaScript workflow engine, a MapReduce-style scaling lane, an egress-enforcing HTTP proxy, a Docker sandbox, an ed25519 signing pair, an encrypted export/import bundle format, a git-synced central library, a pack publishing format, a destructive-command guard for nine CLIs, an MCP server plane, a usage-analytics/optimize engine, and a wire relay in front of the Anthropic API. Every one of them is defensible in isolation. Together, on zero external users, they are the feature creep.

What is unnecessary right now

  • proxy / report wire — an Anthropic-API relay is a different product wearing the same binary.
  • optimize — recommends measuring itself when it has no data; on a fresh project its only output is "run report usage --live".
  • sign / verify — signing infrastructure before a single shared manifest exists. Stage 4 explicitly says decide after handoffs.
  • export / import encrypted bundles — solved by git + secret set for every observed use case.
  • Workflow scaling Phases 2b–6 — optimizing throughput of a feature the strategy forbids promoting.

What is genuinely missing

  • An answer to "did it work?" Nothing verifies a rendered server actually starts. doctor proves the file parses, not that npx resolves — and the tool knows that risk (it warns about bare launchers) without offering a probe. A doctor --probe that spawns each server and reports handshake success would be the highest-value feature on this list.
  • Shell completions. Absent for a 46-command CLI. L1
  • An upgrade path. No self update, no version check. C4
  • Team/CI ergonomics for the common case: "clone this repo, get its agent setup" as one command.

What confuses a first-time user

  1. Being told to run create-profile and getting either a raw JSON consent envelope or four rewritten config files, depending on whether stdout is a TTY.
  2. session start refusing on the project they just created, with the word "trusted" appearing for the first time as an error.
  3. Applied to 0 target(s). printed under a list of four files that were just handled successfully.
  4. Reading "toolset" in the docs and typing "profile" in every command.
  5. doctor going from 0 warnings to 5 by following the recommended path.

What excites a power user

  1. agentstack adapters validate my.yaml → drop into ~/.agentstack/adapters/ → new CLI supported, no rebuild. Genuinely delightful extensibility.
  2. session freeze --name — capture what a run actually used, replay it in CI.
  3. trust --preview emitting a stable surface_digest; the whole consent contract is scriptable.
  4. guard test rm -rf / — instantly legible, instantly shareable.
  5. init --plan as a documented read-only JSON contract.

As a beginner

Steps 1–5 are excellent and would produce the intended "oh, both my CLIs have the same setup now" moment. Then step 6 hands them a consent digest and step 7 tells them their own project is untrusted. Predicted outcome: value received, then abandonment at the first switch attempt.

As an experienced developer

Fine — they will read --help, spot trust, and move on in seconds. Their friction is different: 46 commands with no completions, and no way to upgrade the binary they just installed.

As a power user

Delighted. init --plan, use --list --json, trust --preview, adapter drop-ins, session freeze. This audience is fully served today — and is also the audience least likely to need the product.

How to cut onboarding to the minimum
  1. Make init end trusted. The user just reviewed and approved every declaration in the import preview — that is the trust review. Record the grant from the same consented plan digest and step 7 disappears entirely.
  2. Fold apply --write into init's confirm. The wizard already asks once; two writes need one consent, not two commands. Target: install → one command → done.
  3. Stop recommending create-profile at the end of init. A one-CLI-pair user has nothing to subset yet. Recommend it from doctor after the second project instead.
  4. Print the undo line after every write, not only some.

Together these take the honest beginner path from ten steps with two cliffs to three steps with none, without weakening a single invariant — the consent is still content-bound, still previewed, still revocable.

Modes that should merge or go

  • use --write vs apply --write — both render, differ only by profile selection. One command with --profile would remove a whole concept. Today the docs must explain when to use which ("session is the recommended beginner way; use --write is the stable/offline path") — that sentence is the tell.
  • setup — a hidden alias for interactive init. Two names for one wizard. Delete the alias.
  • create-profile — should be toolset create, and should not also activate. H3
  • run / shim / try / kill — four launch-adjacent verbs. try in particular ("stage, scan, emit a wrapper prompt on stdout") is a clever trick that no one will discover.
  • proxy + report wire — an Anthropic-API relay is a separate product. Split it out or hide it.

Where defaults can replace a decision

  • Scope. Today init imports at project scope, then a note explains servers now exist in two places and suggests --scope global. Pick one based on where the config was found and stop asking.
  • Secret store. Already good: keychain when non-interactive. The interactive prompt is one decision too many for a first run — default to keychain and let doctor offer .env if the keychain is unavailable.
  • Targets. init writes all six detected CLIs into targets.default, so apply creates .gemini/settings.json and opencode.json in a project for tools the user may never open there. Default to the CLIs that contributed config. M4
  • Guard. On by default.

Critical: the plaintext secret file is the least protected file the tool writes 
$ ls -l .agentstack/
-rw-r--r--  38  .env            <-- plaintext GITHUB_TOKEN, world-readable
-rw-r--r-- 422  agentstack.toml

crates/cli/src/secret/env_file.rs calls atomic::write with no mode, so the file lands at 0644 under the default umask 022. The same codebase gets this right elsewhere — grant.rs:314 uses opts.mode(0o600) and machine_policy.rs:202 uses options.mode(0o600).

The module's own doc comment reads: "a .env holds real secret values, never ${REF} placeholders… So the writer also makes sure the project keeps .env out of git." It thought about git and not about the filesystem. On a shared or multi-user machine — the exact environment where a machine policy ceiling matters — every local account can read the token.

Cleanup and uninstall: strong

uninstall previews the complete managed set with plain-language scope labels, removes ~/.agentstack last because it holds the undo ledger, offers --keep-home, and states clearly: "Your agentstack.toml is never touched — this removes rendered output, not your setup." This is better than most commercial tools manage.

One gap: it does not mention the binary itself, and there is no way to remove it (see C4).

Is it safe?

  • Yes on reversibility — nothing writes without --write, every write is recorded and previewed, foreign entries are preserved.
  • Yes on secrets-in-manifests — ${REF} only, verified in the written manifest.
  • No on secret file permissions. C1
  • Unproven on very deep project paths, because of the backup filename scheme. M2

What is genuinely well done

  • The small crates are small on purpose. trust (1,022) and policy (1,427) are deliberately kept as reviewable boundaries with fixed minimal dependency lists. That is the right instinct and it held.
  • Adapters are data, not code. 13 embedded YAML descriptors + user drop-ins, with golden render snapshots and a nightly conformance job whose comment explains itself: "A red run here means a CLI changed its config schema under us."
  • Security invariants are property-tested, not asserted. Policy narrowing per dimension, byte-flip re-gating in trust.
  • The permitted crate dependency graph is written down in docs/ARCHITECTURE.md and "anything not listed is forbidden".
  • Unsafe is concentrated in one file behind a single #[allow].
  • Dependency discipline — Boa is isolated in workflow with module loading explicitly disabled and a witness test for it.

Unnecessary complexity & debt

  • 82% of the code is in the "orchestration shell". STRATEGY.md names the fix (extract the authority data path along existing seams) and TODO.md has it fully unchecked. M1
  • Oversized modules: workflow.rs 4,697 · lib.rs 3,772 · doctor.rs 3,677 · mcp_server.rs 3,300 · grant.rs 2,955 · locked.rs 2,919 · resolve.rs 2,615 · cli.rs 2,238. Eight files over 2k lines is a bus-factor problem for a solo maintainer, and the review notes already flag splitting workflow.rs (F16).
  • Hidden coupling: cli.rs at 2,238 lines is the clap tree — the command surface itself is a single monolith, which is why 46 commands feels frictionless to add and expensive to curate.
  • Duplication risk between the two machine planes. The t3code bridge is fixed-argv actions; the agent-facing plane is MCP tools (agentstack_add_skill, add_server, create_profile). Launch Lane B is explicitly "wrap the mutation logic behind the MCP tools" as new CLI actions — a third caller for the same operations. Watch this; it is exactly how the single-authority rule erodes.
Extensibility: the best-designed part of the system

Adding a CLI is one YAML descriptor, validated by agentstack adapters validate, droppable into ~/.agentstack/adapters/ without a rebuild — and CONTRIBUTING.md names it as the easiest first contribution. This is the single highest-leverage thing in the repo for community growth, and it is mentioned nowhere on the website. Put "Add your CLI in one YAML file" on the landing page.

Documentation review

Twenty HTML pages (~620KB), eight markdown sources under docs/howto/, a tutorial, an examples index, and a 120KB cookbook — plus a CI gate that fails when the docs drift from the clap tree.

Exceptional

  • docs_commands.rs — two-directional drift gate: the "All commands" region must match the clap-tree generator byte-for-byte, and every agentstack <verb> written anywhere in the docs must name a real command. This is the best documentation-integrity mechanism I have seen in an OSS repo of this size.
  • docs/ENFORCEMENT.md and the rule that it wins when any doc disagrees. The honesty invariant ("recording is not prevention; allowed destinations can still exfiltrate") is stated in the docs, not just the code comments.
  • Retired pages are handled properly — noindex, canonical link, meta-refresh, absent from sitemap.xml.
  • Docs CI gates deployment on broken links, fragment checks, sitemap drift, generated-HTML drift, and a headless smoke at phone + desktop widths.
  • The concepts page defines every term in two or three plain sentences.

Missing or wrong

  • No FAQ. No troubleshooting page. Zero hits for either across the whole site. For a tool that writes into six config files on someone else's machine, this is the most conspicuous gap in the documentation set. H6
  • Windows is undocumented — one mention in reference.md, one in an installer error string, while release.yml ships x86_64-pc-windows-msvc binaries. C4
  • Terminology contradicts itself. The house rule says profile→toolset and doctor→check setup. Measured: "profile" 688 vs "toolset" 41 in CLI command strings; 139 vs 33 in docs; "check setup" appears 0 times outside t3code. H2

Engineering quality alone would score 8.5. The overall figure is dragged down by launch readiness — which is the most fixable of the seven.

Why not higher, why not lower

Why not lower: almost nothing here is wrong. The invariants hold, the tests witness them, the docs are drift-gated, the adapters are data, and the honesty is real — including a README paragraph that talks readers out of installing. I found one genuine defect in a security-adjacent path (C1) and it is a one-line fix.

Why not higher: the product has been optimized against a specification rather than against people. Ten steps of the documented happy path produced two hard stops, a summary that reads as failure, three names for one concept, and a doctor that goes from clean to five warnings by following its own advice. Every one of those would have been caught by the first user study — which is precisely the gate that has never been run.

Would I personally use this project?
Yes — and I would have installed it today if I were running two agent CLIs with overlapping MCP setups. doctor and explain alone justify it. I would use apply, doctor, diff, explain and restore constantly, and I would probably never touch workflows, sandbox, signing, or export.
Would I recommend it?
Yes, with one condition: to developers who already feel multi-CLI pain, after C1 and C4 land. I would not recommend it to someone on one CLI — and neither does the README, which is to its credit. I could not recommend it at all today to anyone who cannot upgrade the binary they install.
Biggest strength?
Diagnostic honesty. Not the trust model, not the adapters — the fact that doctor tells you what is wrong, in your language, with the exact command that fixes it, and that the project maintains a written rule that its claims may never exceed what it enforces. ~110 finding templates each carrying a real fix; advisories that deliberately do not count against readiness; a nightly job whose stated purpose is to catch vendors changing schemas under it. Everything else in this product is replicable. That culture is not.
Biggest weakness?
It has never met a stranger. Every gate that requires a person other than the author is open, and the consequences are visible everywhere: the internal vocabulary in beginner surfaces, the trust gate firing at an arbitrary moment, three words for one concept, a JSON consent envelope as the answer to a recommended next step. The project has world-class discipline about code correctness and no feedback loop about human comprehension.
What should be fixed first?
C1 today — one hour, closes a real credential exposure. Then H1: make init record the trust grant from the consent the user already gave. That single change removes the hardest stop in the product, weakens no invariant, and turns the retention journey — profiles and sessions, the feature the strategy is betting on — from blocked to smooth.
What feature would most increase adoption?
agentstack doctor --probe (M10) — spawn each rendered server, complete the MCP handshake, report tool count or the exact failure. It converts the product's answer from "your config is well-formed" into "your setup works", which is the question every MCP user actually has and which no competitor answers. The tool already knows every command, env var and secret; it already warns that bare npx may not resolve under a GUI launcher. It is the shortest distance between this project's existing knowledge and a user's actual anxiety. Runner-up, non-feature: publishing the brew tap and an upgrade command — distribution beats features when the funnel is empty.

Limits of this review

  • t3code was not exercised. It is a private fork; the panel could not be installed or driven. All t3code conclusions are drawn from the CLI-side contract, the parity tests, and the repo's own notes — never from using it.
  • No full test-suite run. Test infrastructure was reviewed (57 integration files, golden snapshots, CI configuration); cargo test --workspace was not executed here, so "the suite is green" is a claim from CI and the roadmap, not one this review verified.
  • No sandbox / egress / Docker paths. Feature-gated and Docker-dependent; assessed from documentation and the enforcement matrix only.
  • No workflow execution. The Boa boundary was not independently audited — the project's own §9.3 review is taken at its word.
  • Not a security audit. C1 surfaced from a file-permission check during the generated-files pass, not from a systematic threat-model review. The trust, policy, and gateway paths were read for structure, not attacked.
  • Single-platform. macOS 25.5 / darwin only. Windows and Linux behaviour was not observed.
  • No real users. The three onboarding personas are informed judgement, not observation — which is exactly the gap C2 is about, and it applies to this review too.
