02

Product, positioning & competition

The product is strongest as a neutral lifecycle manager for agent environments. Security makes portability trustworthy; it should not replace portability as the opening lesson.

Recommended category

Agent environment manager

Promise: define an agent setup once; use it across every coding CLI.

Wedge: detect existing native configurations → import them → preview normalized output → render to multiple tools → diagnose → restore.

Durable moat: the lifecycle around the manifest: adapter conformance, provenance, content pins, consent, safe mutation, drift reconciliation, temporary activation, enforcement, and evidence.

E01E02E06
Ideal initial customer

The poly-CLI developer

A developer already using at least two supported coding tools, with repeated MCP server, skill, instruction, or settings configuration—and enough pain from drift or cleanup to value one source of truth.

  • Primary: individual developers switching between Claude Code, Codex, Cursor, Gemini CLI, and peers.
  • Next: teams standardizing a reviewed project setup without replacing personal setup.
  • Later: regulated or platform teams needing stronger policy, confinement, and evidence.
Differentiator 1

Vendor neutrality

Native vendors optimize their own ecosystem. AgentStack compiles one intent into competing CLIs.

Differentiator 2

Reversibility

diff, managed regions, backups, history, restore, and uninstall reduce trial risk.

Differentiator 3

Trustworthy reuse

Locks, content digests, inert untrusted declarations, and secret placeholders turn sharing into a reviewable act.

Differentiator 4

Honest protection

The enforcement matrix distinguishes unsupported, coarse, proxied, and enforced—not vague “secure by default” claims.

Stress-testing the thesis

Method gap

This review found no problem with the product thesis. Treat that as unverified, not as confirmation.

Every one of the 22 findings is about coherence, process, docs, or two code defects. Not one challenges the premise that poly-CLI portability is a pain worth a tool. That is either because the premise is sound or because nothing in the method could have falsified it — a review that reads source, docs, and release artifacts is structurally incapable of discovering that nobody wants the product.

The tests below are the ones that could return “no.” Each names what would falsify it and the cheapest way to find out. Most fold into the five-user study, which makes that study the highest-leverage item in this report by a wide margin — not because activation metrics matter, but because it is the only proposed activity that can return bad news about the thesis.

None of this is new research scope — it is the difference between a study that measures whether onboarding works and one that can also report that the premise does not.

04

CLI, commands & operating modes

The CLI is mature in safety and orientation, but the full surface is broad. The most important UX repair is to keep “where capabilities live” separate from “how strongly a run is confined.”

CLI strengths
  • Bare-command overview directs the next action.
  • Visible commands are curated; advanced commands remain discoverable through complete help.
  • Dry-run is the default for material writes.
  • JSON/action contracts support automation and t3code.
  • Errors generally include cause, consequence, and exact recovery command.
  • Import, diff, adopt, apply, doctor, restore form a coherent lifecycle.
Complexity debt
  • Dozens of hidden or advanced verbs remain part of the mental model.
  • apply, use, sessions, gateway, locked runs, sandbox, lockdown, workflows, and code mode overlap in language.
  • “Profile” persists in machine-facing surfaces while UI says “toolset.”
  • Protection tiers and delivery modes are easy to conflate.
  • Help/docs can describe source features unavailable in the installed release.

05

Generated files, safety & recovery

Artifact ownership is unusually thoughtful. The remaining product task is to make the full footprint and the difference between “remove managed output,” “reset AgentStack state,” and “remove the binary” impossible to misunderstand.

Source of truth

Project / personal manifests

.agentstack/agentstack.toml (or legacy root form), an agentstack.lock, optional secret source, capability sources, and toolset definitions.

These are user-owned setup inputs, often intended for version control.

Compiled output

Native CLI artifacts

Examples include .mcp.json, CLI-specific TOML/JSON, skill directories, hook/settings sections, and managed instruction regions in CLAUDE.md/AGENTS.md.

Exact output varies by adapter and scope.

Machine state

~/.agentstack/

State ledger, backups, history, trust records, central library and its recoverable lib/.trash/, fetched content store, sessions/runs, usage and footprint caches, adapters, grants, shims, audit/evidence, and personal setup.

Major strength

One managed mutation path

Render planners preserve foreign content, material writes are previewed, history captures undo data, uninstall reuses ordinary empty-manifest plans, and current-source library removals move content to recoverable trash instead of deleting it. That is exactly the right product instinct—provided the new trash restore path is contained and each multi-file operation captures every mutated file.

E08
Clarify

“Uninstalled” still leaves user decisions

At the reviewed snapshot the command loads a manifest, removes managed output and usually ~/.agentstack, but intentionally keeps the manifest, possible plaintext .env, capability files outside managed regions, and the binary. Make three actions explicit: deactivate output, reset all AgentStack data, and remove the executable; support a no-manifest full reset.

Strong boundary

Security invariants are encoded

  • No new unsafe code; existing process management is concentrated.
  • Machine/project policy intersection only narrows authority.
  • Untrusted project declarations stay inert on automatic paths.
  • Pinned byte changes re-gate; no stat-only trust shortcut.
  • Secrets remain placeholders and unresolved values fail closed.
  • Authority construction and upstream dispatch are kept single-path.
  • Adversarial, property, integration, conformance, and race tests exist.
E07E09E11
Concentration risk

The CLI is becoming the system

The workspace separation is meaningful, but most code, tests, state stores, rendering, trust orchestration, UI contracts, sessions, workflows, recovery, and command handling remain in one crate with several multi-thousand-line modules. This raises review cost and makes small changes cross broad compile/test surfaces.

Do not split by line count. Extract the already-defined authority seam—AuthorityGrant → ExecutionPlan → Gateway::try_call → secret resolution/upstream transport—and move pure plan/state domains while preserving one constructor and one dispatch path.

E03E09

Threat-model honesty

Allowed destinations can still exfiltrate; proxy variables are bypassable with an open route; trust is not vetting; host policy is not confinement. Preserve this language.

Adapter system

Descriptors, registry checks, golden fixtures, and conformance automation are appropriate for vendor churn. Prioritize adapters with observed use, not nominal breadth.

Docs drift is architecture drift

ARCHITECTURE.md says nine crates while the workspace has ten and retains old registry/endgame framing. Make generated crate graphs and enforcement checks release gates.

Release split-brain

Source ≠ release ≠ package

Decide before launch

Workflow headline contradicts the gate

Strategy says freeze new categories and keep workflows experimental until ordinary repeated use. The launch plan calls a reviewable workflow the headline while the five-user study is open.

Decide before launch

Primary UI is not obtainable

Not a defect. The CLI is complete and standalone. This becomes blocking the moment a public page tells someone to use t3code.

RESOLVEDF21 · workflow declare claimed a transaction it did not completeTwo gaps: the undo set omitted agentstack.lock, and the durable entry was written only on success.
Evidence
The command captured script, blueprint, and manifest, then called ordinary lock, which writes the lockfile separately — outside the capture. A real declare → restore --last --write fixture removed the three captured files and left the workflow pin and blueprint checksum in agentstack.lock. History was recorded after all writes, so a crash mid-transaction left no durable undo entry at all — while the code comment asserted that “a crash between the two cannot leave a state neither can undo.”
Impact
“One transaction,” “the project is byte-identical to before,” and “one restore entry” were each stronger than the mechanism behind them.
Fixed
Landed. The undo set is now script + blueprint + manifest + lockfile — every file the transaction can touch, not every file it authors. The durable entry is recorded before the first write rather than after the last, which is what makes a mid-transaction kill recoverable; this is safe because the undo records are declarative (restore these bytes / delete this file), so replaying them over an already-clean project is a no-op. A clean failure that rolls itself back fully discards its own entry, so the ledger head stays the user's real last change; a partial rollback keeps the entry and now says so explicitly instead of claiming the project is as it was. An empty workflows/ directory created by the attempt is removed too.
Second round
A follow-up review caught that the first fix still degraded silently: history was recorded with unwrap_or(None), so an unwritable ledger let the declaration proceed with no durable recovery — the exact guarantee the change existed to provide. Recording is now a precondition: it happens before even the workflows/ directory is created, and its failure refuses the command with the project untouched. History stays best-effort everywhere else in the codebase; this command is the exception because undoability is its contract.
Witnesses
Four. Undo of a successful declare reverts the lockfile to its prior bytes. A failure injected at each of five points — including one after the lock has rewritten the lockfile, the only case that exercises rolling back a modified rather than a created file — leaves the project byte-identical with no entry at the ledger head. A fail-point hook snapshots the ledger at every step, asserting exactly one durable entry exists at each, which recording-after-the-writes would have made zero. And an unwritable-history run refuses before any write.

RESOLVED (2nd pass)F22 · A containment invariant the code asserted but did not holdThe defect worth fixing was the false comment and the non-atomic ordering — not the traversal itself.
What was actually wrong
Not a privilege boundary. Exploiting the traversal required write access to ~/.agentstack/lib/.trash/*/entry.toml — the same machine store that holds the locked-run commitment key. Anyone who can edit that record can already do worse directly. Framing this as a security hole overstates it.

The real defect is epistemic. restore carried a comment stating that deriving the destination from the kind meant “a hand-edited record can never write outside the library.” The kind chose the directory; the name was joined onto it verbatim, and a record named ../../../escaped landed a body outside lib/. A comment asserting an invariant the code does not enforce is worse than no comment: it is how the next person, reasonably trusting it, introduces the version that is a boundary.
Second defect: ordering
Independent of containment, the mutations were not walkable-back. restore moved the body before checking that the kind-specific index row existed — so a record missing its row failed with the bytes already out of the trash and absent from the index. --replace deleted the live entry outright before moving the trashed one in, destroying the copy the user had if anything failed next. stash moved the live body before writing the record that describes it.
Fixed
Landed. restore now validates the whole record — name is a plain component, body is one of the two known slots, the index row exists and its name agrees — before it moves a byte, and the derived destination is canonically resolved and checked to be inside lib_home (which also closes the symlinked-kind-directory route the name check alone would miss). Mutations are ordered so each is reversible: body first, replaced entries set aside rather than deleted, index saved last, and the body moved back if that save fails. stash writes its record before moving bytes. The two name predicates — “safe to target a file” and “safe to restore” — were separate and disagreed; they are now one shared rule, so a body is never trashed under a name restore would reject. The false comment is replaced by a statement of what is checked and why.
Second round
A follow-up review found three residual defects. (1) restore displaced the live body before confirming the trashed body existed, so a record pointing at a missing body stranded the user's copy under .trash/<id>/replaced; the source is now validated with the rest of the record, and every later failure puts the displacement back. (2) All four lib remove* paths called stash then saved the index — a failed save left the body in the trash with the index still naming it. They now route through one transaction that undoes the stash on failure, and the index write is atomic. (3) The name rule rejected any embedded .. as a substring, which needlessly refused legal names like a..b; it now rejects the .. component.
Witnesses
Seventeen across the module, including the review's own ../../../escaped fixture verbatim, a symlinked skills/ whose plain name still resolves outside, a record with no index row, a row naming a different capability, an unknown body slot, a record claiming a body that is absent (asserting the live copy is never displaced), --replace preserving the live entry, an unstash rollback, and a full round trip for a name containing dots.
Addendum
The first fix was incomplete — a second bypass survived it. The containment work guarded the destination (a plain name, a resolved-path check, a symlinked dest) but not the source. restore moves the body with rename, which relocates a symlink itself rather than its target — so a crafted .trash/<id>/body symlink was renamed into the live library, which then served content from wherever it pointed. The body-name allowlist did not catch it (body is exactly the expected name) and Path::exists() follows links, so the incomplete-entry check passed too. Reproduced end to end against the release binary: restored skill 'pdf', exit 0, with lib/skills/pdf a link to a directory outside the library. A symlinked entry directory reaches the same outcome one level up.

Now closed. Every component from the trash root down to the body is checked with symlink_metadata (which never follows), and the emptiness check uses it too. Two further defects on the recovery path were fixed alongside: failed rollback moves were swallowed while the error still claimed the entry was “left in the trash, unchanged”, and displace_existing deleted a leftover replaced/ — which is the residue of an earlier incomplete rollback and therefore possibly the only surviving copy of the live entry. Three new witnesses, each mutation-tested against the unfixed code.

Correction to this report's own framing: the original entry called the traversal “not a privilege boundary” because it needed write access to the trash. That reasoning holds for the traversal and it held here too — but it is also what made a partial fix feel sufficient. The stated invariant is that the trash can only ever put bytes back inside the library; a guard that covers one of two routes does not establish it.

Proceed with the product. Pause the broad launch.
