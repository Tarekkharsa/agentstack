Part 2 · Trust DX — the plan simplified · your pick first
THE PROBLEM

Two sentences

The tool re-gates its own edits: add --write flips the digest and demands a fresh trust . for a change you just previewed. And every new project pays the full card even when every byte is already approved elsewhere.

YOUR PICK

Trust happens at lib linkCHOSEN DIRECTION — DRAFT

$ agentstack lib link ~/skills --write
[ full review of the source's content — once, here ]
✓ linked + trusted: source “skills”, 14 pinned digests

$ cd ~/any-project && agentstack use web --write
✓ all content trusted at source “skills” — activated

Linking is the review moment. The one deliberate yes moves to where you adopt the source — after that, projects consuming only source-trusted digests activate without a card.

And --write moves nothing. The folder stays exactly where it is (unlink leaves it alone too). Without --write the command only previews; with it, it records the link. One universal rule across the whole CLI: preview first, --write commits. So yes — agentstack lib link ~/skills alone is enough to see exactly what will happen; add --write to make it so.

Three guards keep it safe:

1Still byte-bound: the grant covers the digests reviewed at link time. New or changed content in the folder re-gates at the source — one diff-first review, not per project.
2Revocation: lib untrust <source> kills every inherited activation at the next dispatch (trust is re-checked at the gateway on every call — already built).
3Executable kinds (hooks, extensions) keep the full per-project ceremony — a skill reads; a hook runs. Different risk, different yes.
FIX 2

The tool's own writes re-pinCOMPANION

$ agentstack add server github --write
✓ added
✓ trust re-pinned — 1 change: + server github

You previewed it, you wrote it — that was the yes. apply already re-pins this way; extend it to add, lock, use. External edits (git pull, editor) still re-gate.

FIX 3

Cards only expand what changedCOMPANION

$ agentstack trust .
✓ 12 unchanged (collapsed) · 2 changed:
  ~ skill web-design   [diff inline]
  + server github
Trust this project?  [Enter · d = detail]

Unchanged and already-approved content collapses to one line. The two re-gate styles become one diff-first card.

WHY --WRITE

Why it exists — and your challenge to itADOPTED — EVERYWHERE

Why it exists: every command that would change something shows the change and stops. --write is the one uniform way to commit. One rule for the whole CLI — you never wonder which commands are dangerous, because none are without it.

Your challenge is fair: in the daily loop it doubles the typing. The honest middle:

$ agentstack add server github
[ preview: + server github, pinned bytes ]
Apply? [y/N] y
✓ added · ✓ trust re-pinned

Proposal: in an interactive terminal, the preview flows straight into a y/N confirm — one command, still nothing silent. Same guarantee, half the ceremony. Decision recorded in this review: adopt it everywhere. --write stays as the explicit form for scripts and agents.

SECRETS

Multiple secrets, .env, varlock

You rarely run secret set at all. Resolution walks a chain; first hit wins:

env var → varlock vault → OS keychain → .env

Already on .env or varlock? Nothing to do — ${GITHUB_TOKEN} in the manifest resolves from there at use time. secret list shows every reference the manifest makes and whether each resolves on this machine. secret set is only for values you want in the OS keychain. Unresolved fails closed — never an empty string.

WHAT IS X

agentstack x, in one paragraph

Not dynamic, not magic: one static namespace. The front door shows 17 verbs; every other command sits one hop behind agentstack x <cmd> — same parse tree, same flags, same exit codes. Every hidden command also runs at its own name: agentstack gateway connect and agentstack x gateway connect are the same command. --help --all prints the whole map.

And not Claude-only: gateway connect <cli> runs once per CLI — claude, codex, cursor… x adapters list shows all 13 known CLIs and which look installed.

THE MANIFEST

One file, all cases — .agentstack/agentstack.toml

# servers — the MCP servers this project may use
[servers.github]
type = "stdio"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-github"]
env = { GITHUB_TOKEN = "${GITHUB_TOKEN}" }   # ${REF} — never a value

# skills — inline (in this repo) or from a linked library source
[skills.code-review]
path = "./skills/code-review"          # inline: overrides any library name
[skills.web-design]
source = "skills"                      # library ref: resolved from the linked source, pinned at lock

# instructions — one base file; variants override per (CLI, model)
[instructions.house]
path = "./instructions/house.md"                # the default EVERY CLI gets

[[instructions.house.variant]]
cli = "claude-code"
model = "opus"
path = "./instructions/house.claude-opus.md"    # only Claude Code on Opus gets this

[[instructions.house.variant]]
cli = "codex"
path = "./instructions/house.codex.md"          # any Codex, any model

# pick order: exact (cli, model) match → cli match → base file.
# delivered per harness over its best channel (MCP initialize, global file,
# flag). Only 6 of 13 adapters have an instruction channel — `status` says
# which one is actually active where.

# toolsets — ONE table on purpose. The strategy makes toolset the single
# selection concept: project selection, lease unit, and workflow role are
# one noun. Which fields you fill decides how it is worn.
[toolsets.web]                          # worn for selection: `use web` activates these
servers = ["github"]
skills  = ["web-design", "code-review"]

[toolsets.reader]                       # worn as a workflow role: who runs it, and how
harness = "codex"                       # which CLI runs this role
model = "gpt-5.5"
effort = "high"
skills  = ["code-review"]               # a role can carry members too

# hooks & extensions — executable kinds: full consent ceremony, always
[hooks.format-on-stop]
# event + matcher + command — rendered into each harness's native hook config

# per-harness native settings
[settings.claude-code]
# dotted keys, e.g. permissions.defaultMode

# policy — can only narrow the machine ceiling
[policy.tools]
"*" = ["!delete_*"]
github = ["get_*", "list_*"]

agentstack.lock sits beside it and pins every resolved ref to exact bytes. The machine file ~/.agentstack/agentstack.toml holds the ceiling ([policy], [guard]) that no project can widen.

POLICY — THE HONEST ANSWER

Can a CLI work around [policy.tools] or the trust logic?

Checked against docs/ENFORCEMENT.md (the Tools row of the matrix). The answer depends on the lane — and the docs say so plainly:

  • Gateway / lease lane — enforced. Every call passes Gateway::try_call: a denied tool is filtered out of discovery and refused if called anyway. Trust is re-read from disk on every call — a revoked yes stops the next call. No workaround through the gateway.
  • Host-rendered lane — unsupported, by declaration. When apply writes a server into a CLI's native config, that CLI talks to the server directly — the policy decision is never called on that path. A harness in host mode can simply use what its own config holds. This is invariant 8 in action: the docs refuse to claim enforcement where there is none.
  • Sandbox — enforced for gateway-routed traffic, with a named ceiling: an agent that opens its own connection to an upstream the egress policy allows bypasses the gateway. Lockdown closes that: the egress sidecar's relay is the sole MCP route and direct connections to declared hosts are blocked.

What else lives under [policy.*]: tools (per-server allow/deny patterns, rename-proof "*" rules) · filesystem (read/write deny globs, enforced strictly in sandbox tiers, advisory on host) · egress rules (where each server's traffic may go — enforced at the proxy in sandboxed lanes). All of it intersects downward from the machine file: a project can only narrow.

Practical rule: if the policy must hold against a hostile agent, run the gateway/lease lane or a sandbox tier. Host mode is convenience with honesty labels, not confinement.
