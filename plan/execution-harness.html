1. The problem, measured

The problem is real, and this repository already pays for it. CLAUDE.md forbids a bare cargo test at the workspace root because the workspace has 60+ test binaries and the run costs minutes. The rule exists because the cost is real; the rule is a workaround, not a fix.

2. The vision — nine layers

The idea, stated faithfully: put an execution harness between the agent and its tools. The agent declares intent — "verify this change", or a confidence level of quick / normal / release — and the harness plans the execution. Integration is meant to be cross-agent: every coding CLI (Claude Code, Codex, Gemini, OpenHands) routes tool execution through the harness, by MCP tool provider, wrapper, command interception or plugin.

#LayerWhat it doesVerdict
1Change analysisWork out what changed from dependency, build and import graphsdelegate-to-tools
2Execution planningTurn declared intent into a concrete set of commandsneeds-correction — plan by selecting tool modes, never by computing a graph
3Content-based cachingKey results on tool + input hash + environment + dependencies + configalready-adopted-seed (A1)
4Tool-native incremental modesDrive cargo check, vitest --changed, nx affected, turbo --filter, bazeladopt-later — the load-bearing layer
5Policy engineRules such as docs = skip, security = always-fullneeds-correction — a skip rule must fall open, never closed
6Confidence levelsMap quick / normal / release onto plansadopt-later
7Parallel schedulingDependency-aware DAG execution of the planneeds-correction — writes must be isolated per branch
8Execution memoryLong-lived knowledge of past runs, across sessionsneeds-correction — extend the recorder, do not add a second store
9Per-tool adaptersKeep the planner tool-agnostic behind small adaptersadopt-later — with the treadmill cost priced in

3. Four corrections

The design carries one dominant risk and three structural ones. All four corrections must be baked into any adopted version.

Correction 1 — a wrong answer must never be cheaper than a slow answer

A cached or skipped PASS is a claim computed from a record instead of from reality. That is the exact defect class the delivery engagement removed from the product: vacuous greens. Rebuilding it one layer down, in the name of speed, would undo that work.

The rule: every skip needs a sound key, and an uncertain key falls OPEN to full execution, never closed to a skip. If the harness cannot prove the inputs are the same, it runs the tool. Slow and right beats fast and wrong, every time, with no configuration option to reverse it. This is also invariant 8 applied to speed: claims must match enforcement, and a cache hit is a claim.

Correction 2 — delegate graphs, do not compute them

Layers 1 and 2 as written rebuild the hardest part of Bazel, Nx, Turborepo and Develocity: affected-graph computation across arbitrary languages. Wrong graphs mean false greens. A graph that misses one edge produces a confident PASS on code that was never built.

The cut: the harness selects and invokes each tool's own incremental mode (layer 4), and never second-guesses a tool's graph with a graph of its own. This removes most of the risk and most of the cost at the same time.

Scope of the competitive claim. This is what is known without deep reading of those products: they exist, and they own their graphs. Nothing here rests on a claim about their internals, their performance or their gaps — no such reading was done for this page. The harness's edge is therefore not a better graph. The edge, if there is one, is that it sits at the cross-agent choke point that none of them occupy.

Correction 3 — parallel and speculative execution must isolate writes

The throughput plan already records this constraint, in its section 7 guard on speculative re-execution. Agents write files directly. A loser killed mid-write leaves partial edits behind, and the tree looks healthy and the build passes — the usual signal does not fire. The plan records two real incidents during the delivery work: one agent left 423 compiling but unverified lines, another left 136 lines across three files.

The constraint: a git worktree per concurrent branch of the DAG, discarded whole on loss. Any design where two branches write into the same working tree is unsafe however fast the kill is, because the kill lands mid-write by construction. Layer 7 does not start before that isolation is designed and witnessed.

Correction 4 — the recorder is the execution memory

Layer 8 must extend the machinery that already exists — digests in crates/core, call and run evidence in crates/recorder — and must not add a second record store. This is invariant 6's spirit applied to memory: authority and dispatch stay single-path, and a second store of "what happened" is a second authority on what happened. One record, one digest scheme, one place a reviewer has to look.

4. Strategic fit and the one-thesis rule

The fit is real. The harness sits at the same choke point as the adopted runtime-governance thesis: one brokered dispatch point between the agent and its tools. Governance decides what is allowed to run; the harness decides how to run it. Same seam, same recorder, same digest machinery. It is not an unrelated product bolted on — it is the second question you can ask at a place you already own.

The fit does not authorize the work. It is still a new capability lane, and v3 forbids starting one before the bar. Fit is an argument for later, not for now.

The one-thesis rule. This is the third thesis in one week — portability, then runtime governance, now execution efficiency. A pre-launch product carries one thesis. A second thesis does not double the audience; it halves the message and doubles the surface that has to be true on launch day. Execution efficiency is a chapter of the governance book, not a new book. It is written down here so it survives without being started.

Enforcement honesty carries over

The same limit that constrains governance in host mode constrains the harness. In host mode, routing tool execution through the harness is cooperative. A CLI that shells out directly is not optimized — and it is not governed either. Only sandbox mode can force the route.

So the harness must never be described as guaranteeing that all execution is planned, cached or governed. It can honestly claim: the calls that go through it are planned and recorded. Everything else is a bypass, and the product must say so in the same sentence it makes the claim (invariant 8).

5. What is already adopted

Two items from the throughput plan are adopted, and they are the only adopted parts of anything on this page:

  • A1 — deterministic tool-result cache keyed by content digest. The key is (tool name, normalized argument digest, input content digest); for cargo check -p X it covers the crate source tree digest, the lockfile digest and the toolchain. Only read-only tools declared deterministic take part; never cache a tool that writes, never cache across the trust gate, never cache anything that resolves secrets. The key is content, never time, so invariant 4 holds. Source: throughput plan, section 5, A1. It touches digest computation, so it is flagged there for line-by-line review.
  • A3 — batch independent tool calls in one turn. Authoring guidance, near-zero code, no new surface. Source: throughput plan, section 5, A3.

A1 is the seed of layer 3 and nothing more. Adopting a digest-keyed cache does not adopt a planner, a graph, a DAG scheduler or a cross-agent integration. Everything else on this page starts only on explicit maintainer adoption after the bar is met.

One bookkeeping note, recorded rather than resolved. The throughput plan's own "cheap subset" option names A1, A3 and B3 together, and the plan's status line still reads "proposal, not adopted work"; TODO.md carries no entry for any of them. The adoption of A1 and A3 recorded here comes from the maintainer, not from those files. Whoever acts on this should reconcile the three documents first.

6. Triggers — what would justify starting

Any one of these is a reason to reopen this page. None of them is met today.

  1. The activation study reports participants stalled on verification cost. If the instrument for the bar-met moment shows real users waiting on verification rather than on the product's own concepts, the problem is on the critical path to activation, not beside it.
  2. Measured AgentStack-runner data shows the same waste profile. Not Claude Code session data — AgentStack's own runner, under its own load. This closes the gap that throughput plan 2.6 opened and that section 1 carries forward.
  3. A named competitor ships a cross-agent execution cache. The claimed edge is the choke point, not the graph. If someone else takes the choke point, the edge is gone and the calculation changes.

7. Risks

RiskSeverityWhat it means
False greensDominantA skipped or cached PASS reports on a record, not on reality. Reintroduces the defect class the delivery engagement removed. Correction 1 is the only acceptable answer: uncertain keys fall open.
Cache-key soundnessHighThe key must cover every input that can change the answer — source, lockfile, toolchain, environment, config. A missed input is silent and produces exactly the failure above.
Side-effect isolationHighConcurrent and speculative branches write files. Without a worktree per branch, a discarded branch corrupts the tree while the build still passes (throughput plan, section 7; two real incidents).
Cooperative vs. enforced routingHighIn host mode a CLI can shell out and bypass the harness entirely. Only sandbox mode forces the route. The claim must be scoped to calls that actually pass through.
Scope — a second unvalidated productHighA planner, a policy engine, a scheduler and a memory are a product in themselves, proposed before the first product has met its bar. Third thesis in one week (section 4).
Per-tool adapter maintenanceMediumLayer 9 is the same treadmill as the 13 CLI adapters already in crates/adapters/descriptors/ (count read from the repository, 2026-08-05) — except each new adapter must track another tool's incremental semantics, where being wrong produces a false green rather than a bad config file.

8. The thesis, in one line

Governed execution can also be efficient execution — at the same choke point, later.

Agents decide what. AgentStack decides how. That framing is worth keeping. It is not worth starting before the bar.
