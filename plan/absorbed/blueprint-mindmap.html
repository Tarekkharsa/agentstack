YOUR QUESTIONS

Answers, short — with my evaluation where you asked for one

Q1 · Do I have to run lib sync in my skills folder?SHIPPED
No. Three steps, nothing else:
  1. Put skills in any folder — a git clone is just a folder (git clone …/skills ~/skills).
  2. Link that folder once. It becomes a library source.
  3. Pick skills in a project. The exact bytes are pinned in the project lock.
lib sync is optional. It is a convenience for pull/push when the folder happens to be a git repo. Plain folders work exactly the same.
Q2 · Is a separate init step the right design for the live lease?
Today: the lease serves what the manifest declares, so a manifest must exist, and init is the step that creates it (and imports your existing CLI configs).
MY TAKE The manifest is right — without a declaration there is nothing to pin, nothing to trust, nothing to serve. The ceremony is not. The strategy's own design law says: automate everything except the yes, and it calls the manifest machine-written. So a fresh project should not need an explicit init: the first real action (use, add, apply) can materialize .agentstack/ silently, and the only stop is the yes. Recommendation: fold init's project-side half into the first action; keep init as the machine-adoption verb. This touches open decision F6 (where gateway connect belongs) — same family: fewer ceremonies, same guarantees.
Q3 · Nested folders become toolsets automatically (web/web-design-skill → toolset web)?IDEA
Not in any document today. Linked folders are shipped; the auto-toolset mapping is new.
MY TAKE I support it — it is the identity line made real: “feels like a filesystem, thinks like a vault.” A folder is already how you think in groups; the toolset should follow. Three guards make it safe: (1) the mapping materializes into the manifest with a preview — a suggestion at link time, never ambient magic at runtime; (2) only first-level folders map to toolsets, so deep nesting stays unambiguous; (3) a folder rename prompts — it never silently rewrites toolset names in the lock. Route it into the named design-doc slot for source precedence rules, and it needs your adoption first.
Q4 · I trusted a skills repo once — trusting it again per project is bad DX.OPEN
Per-project consent is deliberate: the project is the blast radius, and one yes covers exactly one project's use of exact bytes.
MY TAKE You can get the DX without touching the invariant. The strategy already promises it: consent “compressed into a single glanceable, content-bound moment — compressed, never removed.” Concretely: when the digest you are approving is already trusted in another project, the card should open as one glance — “identical to what you approved in project X — unchanged” — one yes, zero re-reading. Recognition state for this already exists on disk (~/.agentstack/recognition.json). That is presentation compression, not consent removal. A true per-source global grant is also possible, but it widens what one yes covers — only you can trade that, and it presses on invariant 4. Recommendation: glanceable re-trust now; measure the residual friction inside F9; revisit global grants only if the study shows the friction still bites.

AREA 6

Adopted direction — how it works

  • Status: drafted + argued · binds nothing until you adopt R2
  • Concede install: no transitive resolution · no semver · no update tooling · no registry race
  • Govern intake: external ecosystems (APM, vercel-labs/skills, MCP registry) are machine-readable supply → search/add-from stage it inert → trust gate shows the full review → your yes → digest pinned. You never own their shelf; everything off it passes your gate.

  • Beachhead unchanged: one developer, 2+ CLIs · enterprise = named trigger, not a lane
  • Tripwires: APM ships runtime enforcement · vendor config-import convergence
