Trust DX — the rethink

Everything below is changeable, including the invariants — they are the maintainer's, not the documents'.
Facts are from the code as of today; every claim carries its file.

1 · TODAY

The flow as built — where the yes actually lives

  • Only two verbs render a card and write a grant: agentstack trust [path] and agentstack yes. Everything else refuses at use time and names trust . (session start, lease open, run).
  • One composed card per project, one yes. The grant is stored per (project path, digest) in ~/.agentstack/trust.json — never per capability, never per source. (trust.rs:365, lib.rs:76)
  • The card: summary (“This project will: run N commands · contact N hosts · read N secrets”), a recognition line, then the full grouped body with + / ~ / − diff markers, then blockers. (trust.rs:1667–2800)
  • Recognition today is one line of prose. “all 4 items are already approved in 2 other projects” — and then the full body prints anyway. (recognition.rs:10–14)
  • Two different re-gate experiences. Manifest/lock byte changes → diff banner on the next trust. Pinned content drift → inline line-diff + a per-item accept/keep/block prompt. One git pull can trigger both in one card. (regate.rs, trust.rs:2160)
  • Headless: --yes requires a --consented-digest obtained from a separate trust --preview round-trip; agentstack yes refuses without a TTY entirely. (cli.rs:1016, yes.rs:98)
2 · THE PAIN

Where the annoyance actually comes from

  1. The tool re-gates its own edits. add --write and lock --write change manifest/lock bytes, which flips the consent digest — so the ordinary editing loop mechanically invalidates trust and tells you to run trust . again for a change you just previewed and confirmed. (add.rs:1560) This is the single biggest source of “again?”.
  2. Every new project pays the full card even when every byte is already approved elsewhere — recognition changes one line, not the work.
  3. Two re-gate UXes that look and behave differently for what feels like the same event (“something changed”).
  4. Headless needs a two-step dance (preview → digest → yes) that agents and CI stumble over.
  5. The activation study already plans to measure exactly this: D2 — the re-trust friction watch — hypothesis: “cheap once, expensive in aggregate.” (activation-study.md:223)

Note a precedent already in the code: when agentstack itself rewrites the manifest and trust was valid before, apply silently re-pins (✓ trust re-pinned, apply.rs:1295). The principle exists; it is just not applied to add/lock/use.

OPTION A

Glanceable re-trust — compress the presentation, keep every yesNO INVARIANT TOUCHED

Rule: the card only expands what is new. Unchanged and recognized content collapses to one line; the yes stays.

$ agentstack trust .
Reviewing ~/proj-b …
This project will: run 2 commands · contact 1 host
all 4 items already approved in 1 other project
[ full grouped body — 40+ lines,
  every skill, every server, again ]
Trust this project?
OPTION A — same moment
$ agentstack trust .
Reviewing ~/proj-b …
✓ all 4 items byte-identical to proj-a — unchanged
This project will: run 2 commands · contact 1 host
Trust this project?  [Enter = yes · d = full detail]

Same rule on re-gates: a card after git pull opens with only the ~ changed items expanded (their diffs inline), everything else one collapsed line. And the two re-gate paths merge into this single diff-first card.

WINSCOSTS
Kills pain 2 and 3 · zero security change — “compressed, never removed” is already the strategy's own promise Rendering work in trust.rs · a collapsed card must still be expandable before the yes (d key), or the yes is less informed than today
OPTION B

The tool's own writes re-pin — consent moves into the previewREDEFINES THE MOMENT, NOT THE GUARANTEE

Rule: when a byte change was produced by an agentstack command the user just confirmed with --write, and the full change was shown in that preview, the same command re-pins trust in the same breath. Human edits and external changes (git pull, editor) still re-gate exactly as today.

TODAY
$ agentstack add server github --write
✓ added
· trust re-gates on this edit:
  run `agentstack trust .` to re-consent
$ agentstack trust .
[ full card again ]
OPTION B
$ agentstack add server github --write
[ preview showed: + server github, pinned bytes ]
✓ added
✓ trust re-pinned — 1 change: + server github

This generalizes two things that already exist: apply's silent re-pin (apply.rs:1295), and the F5 display rule — never pin bytes that were not displayed (trust.rs:2840). The preview is the review; --write is the yes for exactly those bytes.

WINSCOSTS
Kills pain 1 — the loop that generates most re-trust moments disappears · headless agents stop hitting the two-step dance for self-inflicted edits The consent moment is now two shapes (card yes, preview-write yes) — docs must say so honestly · scope must be exact: only bytes fully shown in the preview, everything else re-gates
OPTION C

Trust the source once — grants at the library, projects inheritWIDENS WHAT ONE YES COVERS

Rule: review and approve a linked source's content once (at lib link or first use). A project consuming only source-trusted digests activates with a one-line confirm instead of a full card.

$ agentstack lib link ~/skills --write --trust
[ full review of the source's content — once ]
✓ source “skills” trusted at 14 pinned digests

$ cd ~/any-new-project && agentstack use web --write
✓ all content trusted at source “skills” — activate here?  [Enter]

The consent-card design doc explicitly fenced this off: machine-level standing approval “is a widening of the gate, not a presentation of it, and gets its own review.” (consent-card.md:262). This page is that review's opening argument — the fence is a decision, and decisions are yours.

WINSCOSTS
Matches the mental model exactly — “I trusted this repo already” · new-project cost drops to one line One yes now activates content in projects that did not exist when you gave it — with different secrets, different policy reach · byte-change re-gating must still hold per source · needs its own revocation story (lib untrust) and a per-project opt-out
RECOMMENDATION

Sequence: B, then A, then measure — C only on evidence

  1. B first. It removes the mechanical re-gate loop — the majority of all trust moments — and it is the smallest honest change: the user already said yes to those exact bytes seconds earlier.
  2. A second. Recognition becomes collapse, the two re-gate paths merge into one diff-first card. New projects become a glance.
  3. Then measure. D2 in the activation study already counts the remaining re-trust moments. If the aggregate still bites after A+B, that is the evidence C needs.
  4. C is a real option, not a taboo — but taken on evidence, with its own revocation and opt-out design, because it changes whose future projects a yes reaches.
ONE MORE THING Headless deserves its own small fix regardless: agentstack yes --preview-and-consent — one command that prints the surface, computes the digest, and consents to exactly what it printed, for CI and agents. The two-step dance today exists to keep the reviewed bytes and the consented bytes identical; one command can hold that property by construction.
