1. What each product is

APM is the Agent Package Manager from Microsoft. It is a dependency manager for agent context. It installs skills, prompts, instructions, hooks and MCP servers into many agent tools. It has a manifest (apm.yml), a lockfile (apm.lock.yaml) and a policy file (apm-policy.yml).

APM states one boundary again and again:

"apm-policy.yml governs what gets installed; your agent harness governs what runs. The two planes do not overlap."

"APM is an install-time gate, not a runtime sandbox."

AgentStack is your product. It does the same install-plane job. It then adds a second plane that APM refuses: runtime enforcement. It has a trust gate, policy intersection, a Docker sandbox, an enforced egress proxy, a call recorder and a governed executor.

This is the key difference. APM stops where AgentStack starts.

Two structural differences:

  1. APM deploys much more content per target. It writes agents, commands, prompts, rules, steering files, hooks and skills. You write MCP config, skills, instructions, settings and hooks. APM transforms rule formats per target (.mdc for Cursor, steering for Kiro). You do not.

6.2 The one large hole in APM

APM has an executable trust gate for hooks, MCP, bin/ and canvas. The gate is off by default.

From src/apm_cli/security/executables.py:

"Projects that omit the block entirely get backward-compatible behaviour (all executables deployed)."

The result: on a normal repository with no allowExecutables block, apm install <third-party-package> writes that package's hook commands into .claude/settings.json or .cursor/hooks.json. There is no prompt, no signature, no allowlist and no sandbox. The hooks then run at your permission.

APM applies the strong model to a different thing. Its lifecycle scripts use always-on default-deny, keyed to a SHA-256 of the lifecycle: subtree, and re-gate when the bytes change. That is your trust model. APM applies it only to its own manifest, not to dependency hooks.

AgentStack does the opposite, and does it right. Your standing rule says hooks are an executable capability kind. The full consent ceremony always applies. PackageMemberKind is Skill | Server | Instruction only, so a package reference can never carry a hook. That is a real and defensible advantage.

6.3 Secrets

APM splits by target:

  • VS Code, Copilot CLI, Kiro, JetBrains — APM writes a placeholder. The tool interpolates at runtime.
  • Codex, Gemini, Cursor, Hermes — APM resolves the secret at install time and writes the literal value to disk, mode 0600. .codex/config.toml and .cursor/mcp.json are inside the repository.

AgentStack uses secret_mode: literal for all 12 MCP adapters. The manifest keeps ${REF}; the native config gets the value. You also have agentstack secret with the OS keychain, which APM does not have.

Both write literal secrets. You have a better store for them. Neither writes placeholders where the tool cannot interpolate.

6.4 Honesty

Both projects are honest. This is unusual and worth noting.

APM says: "APM does NOT sandbox MCP servers at runtime, does not do malware analysis, does not sign packages." It tells readers to write "APM dependency governance" in compliance papers, not "supply-chain signing".

You say: "a lock is not trust, trust is not policy, policy is not a sandbox, audit is not enforcement." Your enforcement matrix marks unsupported instead of advisory.

APM adds a "honesty contract" in CONFORMANCE.md: "A requirement marked skipped carries a written waiver; this is debt, not coverage."

Neither product oversells. You are level with them here.

7. Standards and conformance

APM publishes OpenAPM v0.1 — a formal specification with 110 numbered requirements, four JSON schemas and four conformance classes. Tests bind to requirement ids with @pytest.mark.req("req-lk-012").

Two gates are novel and worth copying:

  1. orphan_check.py demands exact set equality across four views of the same 110 ids: the spec anchors, the YAML manifest, the appendix table and the pytest markers. A gap in any one fails CI.
  2. mode_b_detector.sh — the "silent extension" detector. If a pull request touches a critical path, adds 20+ lines, and changes no spec text and no requirement marker, CI fails. The author must write apm-spec-waiver: <reason>. This stops code from growing past the specification without a decision.

APM admits the limit: there is one implementation, and the spec calls itself a working draft. The conformance system measures assertion coverage, not behaviour.

AgentStack has no equivalent. Your docs/reference.md drift check and your ui_contract.rs closed action set are the nearest things. Your nightly live-CLI check is behavioural, which APM's is not.

10. Where each product wins

APM is ahead on

  1. Dependency resolution. A real graph, transitive, with semver ranges, cycle detection and a why walker. You have none of this.
  2. Content deployment breadth. Agents, commands, prompts and rules, with per-target format transforms.
  3. Test depth. 28k tests, red-team suite, mutation testing, meta-tests.
  4. Ecosystem. 93 authors, 73 releases, real users, Microsoft's name.
  5. The specification. OpenAPM v0.1 and the two conformance gates.
  6. Enterprise install paths. GHES, mirrors, proxies, air-gapped bundles.
  7. Lifecycle commands. outdated, update, prune, find, view.

AgentStack is ahead on

  1. Runtime enforcement. Sandbox, lockdown, egress proxy with SNI check and anti-SSRF, gateway as the single dispatch point. APM has nothing here and says so.
  2. The trust model, applied to the right things. Content-bound consent, no digest cache, re-checked at every dispatch. Hooks always get the full ceremony. APM's gate is off by default for the path that third-party packages use.
  3. Secret storage. OS keychain. APM has no store.
  4. Live adapter verification. The nightly run asks the real CLI to read your file. APM does not do this.
  5. Audit. Keyed-hash call records, run events, trust mutations. APM has no runtime record.
  6. Architecture discipline. Ten crates with a stated dependency law. executor and workflow have zero internal edges, so Boa cannot reach enforcement. adapters cannot reach policy.
  7. Reversibility. undo and adopt. APM has cleanup and drift detection, but no timeline.
  8. Release integrity. Provenance attestation and checksum-verified install.

11. What this means for strategy

Three conclusions.

First: APM does not compete with your core claim. It refuses the runtime plane in writing, in six files. Your enforcement matrix is a product APM has decided not to build. Your STRATEGY.md tripwires watch eve and vercel-labs/skills. APM is a fourth tripwire, and it is bigger than the other three. But it is a tripwire on the install plane only.

Second: the install plane is where APM will beat you. A user who wants "install this skill from that repo, with its dependencies, pinned, in every tool" gets a better answer from APM today. Transitive resolution and semver ranges are the reason. You should decide, deliberately, whether you compete there or concede it.

Third: APM's default-off executable gate is your clearest opening. APM writes third-party hook commands into .claude/settings.json with no consent. Your standing rule forbids exactly this. That is a real, demonstrable, security difference. It is also the kind of thing that a single blog post can show.

12. What I recommend

I do not recommend that you start work. Your STRATEGY.md says the shape is committed, and item 11 is the only open item. These are proposals for you to adopt or refuse.

Do not start now, but record:

  1. Add APM as a named competitive tripwire in STRATEGY.md. It is the largest one. Name the trigger: "APM ships a runtime enforcement plane."

Consider after the bar is met:

  1. Transitive dependency resolution. This is the gap that a user will feel. Your [packs] model is the seam.
  2. Version ranges against git tags. Second-largest gap.
  3. outdated and update. Cheap, and the absence is visible.

Consider copying, at low cost:

  1. The silent-extension gate. APM's mode_b_detector.sh idea maps well onto your docs/ENFORCEMENT.md: if a pull request touches crates/trust, crates/policy or crates/egress and does not change the enforcement matrix, demand a written waiver. This directly serves your "claims match enforcement" invariant.
  2. A red-team test directory. APM has 161 adversarial tests in five named groups. Your security claims would carry more weight with a directory that is visibly adversarial.
