P0 — CI is red. The example suite fails.

Size: half a day. Status: DONE — 8e48305 and 299a88b. All 14 CI scripts pass.

What it took, and the second half nobody expected. 8e48305 routed each script to the lane it actually demonstrates. Then 299a88b found the rest: seven scripts failed loudly, and three further assertions had gone vacuous — they passed only because apply no longer opened the file they inspected, so the check read nothing and agreed with itself. A failing assertion announces itself. A vacuous one does not, and it is the same defect as everything else in this document: a claim computed from a record — here, an empty one — instead of from reality.

Running examples/first-value-demo/run-demo.sh against the current build prints:

FAIL  delivery should route MCP servers live on both MCP-capable tools
FAIL  the live lane should report zero project artifacts
FAIL  doctor should be clean after the import (exit 0)

.github/workflows/ci.yml runs ten asserting scripts in its Example suite (asserting) step, plus malicious-repo-demo/run-demo.sh and sandbox/conformance-smoke.sh nearby. None of them opted into [delivery] render_locally, and they assert that apply writes server configs — which it no longer does.

Per script, the decision is a single question: is this demo’s subject the rendered lane, or the live lane? If it is the rendered lane, opt its manifest into render_locally = true and add a comment saying why. If it is the live lane, rewrite its assertions to the new default. Do not opt a script out just to make it pass.

first-value-demo is the product’s headline proof. It should demonstrate the new default, not opt out of it.

Root cause, recorded. Across thirteen rounds every agent was instructed never to run the full test suite, to protect time. The example suite is not cargo test — it is the CI gate and an asserting end-to-end witness — and it fell in that gap.

Done looks like: green CI, and the example suite added to the loop for any delivery change.

R1 — report the APM executable-gate discrepancy to Microsoft, privately.

Slot: do this first among part two. Size: an hour. Time-sensitive. Status: OPEN — maintainer-owned.

microsoft/apm’s published documentation says the opposite of its code. microsoft.github.io/apm/enterprise/security/ states “APM blocks executable primitives from dependency packages by default: hooks, bin/ executables, self-defined MCP servers, and canvas extensions”, and the README says “Secure by default”. But src/apm_cli/security/executables.py on main says, verbatim:

Projects that omit the block entirely get backward-compatible behaviour (all executables deployed).

The gate turns on only when a project or an org policy opts in. So a normal repository with no allowExecutables block gets third-party hook commands written into .claude/settings.json with no prompt, no signature and no sandbox.

This is a documentation-versus-enforcement mismatch in a security control — invariant 8, in someone else’s product.

Report it privately, before writing anything public. Reasons, stated plainly: real users may be affected; AgentStack has a commercial interest in the finding being damaging, which is exactly when disclosure discipline matters most; and leading a launch with an attack on a Microsoft project defines the product by its competitor. If they fix it, you were right and you behaved well. If they do not, the finding remains and you have standing to discuss it.

Note the window is closing: allowExecutables is already deprecated in favour of executables.allow, with a migration helper, so the area is under live development.

R4 — verify whether the workflow dispatcher consumes StepOutcome::Awaiting.

Slot: before any throughput work. Size: an hour. Status: ANSWERED — no change needed.

This is the throughput plan’s own B3, and it was the right thing to do first because it is cheap, checkable, and it changes the value of everything else in that plan. StepOutcome::Awaiting (crates/workflow/src/lib.rs:277-285) exists so the host can step as soon as any one child finishes rather than joining a batch. The plan asserted this was unverified. It is now verified, by inspection.

Dispatch is already continuous, not batched. crates/cli/src/commands/workflow.rs:964 reads:

let wait_for = if replay.is_some() { outstanding } else { 1 };

On the live path the dispatcher blocks for exactly one completion, drains whatever else is ready, and steps again — so a later stage’s child overlaps an earlier stage’s child and the straggler tail is paid once per run instead of once per stage. Only an active resume journal joins the whole batch, and that is deliberate: replay must reproduce the recorded order. A witness test, a_later_stage_child_overlaps_an_earlier_stage_child, already guards the behaviour, so this is not a claim that can quietly rot.

Consequence for the throughput plan. The parallelism workstream that assumes a batch barrier is unnecessary — the barrier it was written to remove does not exist. That is the second workstream measurement has removed from that plan, after D0. Both were killed by an hour of looking rather than by a week of building, and that is the plan’s most valuable property.

R7 — record the side-effect constraint on speculative execution.

Slot: before any C2 work; a design note now, not code. Size: a note. Status: DONE — the note is in plan/agent-throughput-plan.html, committed beside this document.

The throughput plan’s C2 proposes running two copies of a slow task with different hints, taking the first result and killing the loser. Hadoop can do that because its tasks are idempotent and write nothing until commit. Agents write files.

This exact failure mode occurred twice during the delivery work: an agent died mid-task and left 423 compiling, unverified lines in commands/lib.rs, and another left 136 lines across three files. Both times the tree looked healthy and the build passed. Deliberately killing a loser mid-write produces the same state on purpose.

C2 needs the loser’s writes isolated — a worktree per speculative copy, discarded on loss — or it is not safe. The plan does not mention this.

R8 — copy APM’s silent-extension gate.

Slot: after P0–P1. Size: half a day. Status: DONE — 06a9957.

APM’s mode_b_detector.sh fails CI when a pull request touches a critical path, adds 20 or more lines, and changes no specification text and no requirement marker; the author must write an explicit waiver. It stops code growing past its specification without a decision.

The AgentStack version: when a pull request touches crates/trust, crates/policy or crates/egress and does not change docs/ENFORCEMENT.md, demand a written waiver. This directly serves invariant 8, “claims match enforcement”, and it is the cheapest structural defence against the exact drift this engagement kept finding — code and documentation disagreeing with nobody noticing.

What the gate found when it was pointed at history. Over the last 40 non-merge commits touching crates/trust, crates/policy and crates/egress, 21 fire and 19 pass; 20 of the 21 change production enforcement code with no paired claim update. Read that as an upper bound, not a rate: the gate runs per pull request, and some of those commits sit on branches that updated docs/ENFORCEMENT.md in a later commit on the same branch. The honest statement is that at most 20 enforcement changes shipped without a paired claim, not that 20 did.

The gate arrived carrying the defect it exists to catch. Its docstring said it exempted test code; its implementation exempted only tests/ directories — and this repository’s dominant convention is the inline #[cfg(test)] module. So the description and the behaviour disagreed, in the tool whose whole purpose is to catch descriptions and behaviour disagreeing. It was found and fixed before landing. Worth recording, because it is the cleanest possible demonstration that a self-test proves nothing about the world.

N3 — five deliberate SIGPIPE pipelines in device-onboarding/assert.sh.

Size: a note now; an hour if the script ever changes. Status: OPEN.

Five pipelines in examples/projects/device-onboarding/assert.sh can leave a producer writing into a closed pipe. They were left in place on purpose: the script sets set -u and nothing else — neither -e nor pipefail — so a SIGPIPE on the left-hand side of a pipe is discarded and the assertion behaves correctly today.

That safety is entirely a property of two options being absent. If the script ever gains pipefail, all five must be fixed in the same change — otherwise they begin failing intermittently, on buffer-size luck, which is the hardest kind of CI failure to diagnose and the same class of accident that 299a88b already cleaned up once.

The pattern

Every defect in this engagement had one shape: a claim computed from a record instead of from reality.

apply and doctor each held the routing check as a private closure, so four other writers never had it. The abandoned-file detector trusted a state ledger, so a cloned config was invisible. Rules (a) through (e) of the guard verified that every command the product names is runnable and findable — and all five passed while use --write wrote a file that four surfaces denied existed. Rule (f) walks the filesystem; it is the first rule that reads the world rather than the product’s own claims.

P0 is the same lesson one level up, twice. The example suite went unrun for thirteen rounds because it was not cargo test — the loop checked the loop’s own definition of the work, not the work. And when it was finally run, three of its assertions turned out to be vacuous: green because they inspected a file apply no longer opened. The suite drives the real binary end to end, and it belongs in the loop for any delivery change.

R8 supplied the purest specimen of all. The enforcement gate’s own self-test passed while the gate misfired on this repository’s dominant test convention, because the self-test and the gate were both computed from the same wrong idea of where test code lives. Every failure in this list was green, and every one of them was only ever checking itself.

The plan documents show the same shape one level out. The throughput plan measured one system and prescribed changes to another; the APM comparison made confident negative claims about a competitor’s codebase without reading enough of it to support them. Both were the engagement’s single defect in a new place — a claim computed from a record instead of from reality — and both were cheap to fix by going and looking. Both have now been fixed that way, in 34c0db9 and in the throughput plan committed beside this document.
