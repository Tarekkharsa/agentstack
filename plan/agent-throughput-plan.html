1. Summary and the decision asked for

Replacing the workflow JavaScript runtime gives zero measured gain. It would most probably lose speed. The engine is not running while the time passes.

The time goes to two places. The first is model round trips. Each agent makes 65 tool calls, and 16.5 s of agent wall time falls to each one — a derived figure, mean agent duration ÷ mean tool calls, not a measured per-call latency (see 2.4). The second is coarse work partitioning. Runs use 3 to 7 agents, each one 17.8 minutes long, so the achieved parallelism is only 1.22×.

This plan proposes four workstreams. Each one attacks a measured cause:

  • A — cut tool round trips. The largest payoff.
  • B — raise real parallelism. Finer partitions, wider fan-out.
  • C — straggler control. The slowest agent bounds the run.
  • D — cache-affinity routing. Measured, then rejected. See section 8.

This is a proposal, not work. STRATEGY.md v3 forbids starting a new capability lane before the bar is met. The maintainer must adopt this plan, adopt a subset of it, or shelve it. Nothing starts before that choice.

2.2 What drives agent duration

Two correlations were computed across all 57 agents:

  • Tool call count against agent duration: R² = 0.69
  • Token volume against agent duration: R² = 0.43

Tool round trips drive duration more strongly than token volume. This is the single most important measurement in this document. It sets the order of the workstreams.

2.4 "16.5 s per tool call" is derived, and what it contains

It is 17.8 min ÷ 65 = 16.5 s: mean agent duration divided by mean tool calls. No per-call latency was measured. The number therefore absorbs everything else the agent does between calls — model thinking time, output generation, and the real execution time of the commands themselves. The 155 min of bash time in 2.3 is inside this figure, not beside it: 51.0 min of cargo, at a 23.2 s mean over 132 calls, is work the machine actually performs.

This weakens workstream A's headline, and the plan should say so. The 39% figure in section 5 assumes that removing a tool call removes 16.5 s of wall time. That holds only for the part of the 16.5 s that is round trip. When a tool gets richer, the round trip goes away — the work does not. A single call that greps, reads six files and returns a symbol with its callers still does the reading. A cargo check folded into a richer tool still compiles for 23.2 s. Read A's payoff as an upper bound with an unmeasured discount, and measure a real per-call breakdown before anyone commits to 39%.

2.5 The two populations, and what does not reconcile

This document measures two different populations, and they are not stated in a way that lets a reader reconcile them:

  • Section 2 — 57 agents across 12 workflow runs, 6.28 M "Tokens".
  • Sections 5b and 8 — 86 agent transcripts, 6,997 assistant turns, 509.8 M input tokens.

Two things are unresolved. First, whether the 86 transcripts include the 57 agents — 86 > 57, and the most likely reading is that the transcript set is a superset that also covers agents outside the 12 runs, but the underlying records were not re-checked to confirm it. Second, what "Tokens: 6.28 M" means. It cannot be total input, because 5b reports 509.8 M input for a larger but overlapping population — two orders of magnitude apart. The most likely reading is that it is a non-cached or billed-token figure from the workflow run records, while 5b counts raw message.usage input including the 96.7% that is cache reads. That was not verified, so it is recorded here as unknown rather than asserted. Anyone who needs a token figure from this document should re-derive it from the records and fix this section, and no cost argument should be built on the 6.28 M number until they have.

2.6 What was measured is not what the plan proposes to change

All of the evidence above comes from ~/.claude/projects/ — Claude Code sessions. The plan proposes changes to AgentStack's own workflow runner. These are different systems: a different scheduler, a different concurrency model, and a different process boundary (Claude Code runs agents in-process as async generators; AgentStack spawns a child process per agent — see the table in section 3). Measurements taken on one do not automatically hold on the other.

Which items transfer, and which do not:

  • Transfers. A1 (a deterministic tool-result cache) and B2 (finer partitioning) rest on properties of agent work itself — repeated deterministic reads, and context growing with agent length. Those hold on either host.
  • Does not transfer. B1's concurrency raise is the clearest case. The "4 vs ~10" comparison sets an AgentStack constant against a Claude Code one, and the 1.22× parallelism that motivates raising it was measured on Claude Code. AgentStack pays a child-process cost per agent that Claude Code does not, so its optimal concurrency may be lower, not higher. Nobody should act on B1 without first measuring AgentStack's own runner under its own load. That measurement is a prerequisite of B1, not a follow-up to it.

3. Why a runtime change gives zero

Compare the two engines directly.

Sandbox purposeDeterminism for the resume cacheReal capability denial (no fs, net, process, eval, modules, timers)

Three reasons an engine swap cannot help:

  1. The engine does no measurable work. The scripts are 200 to 400 lines of composition. They call agents and combine results. The measured scheduler delay is 0.98%, and that number is slot waiting, not script execution.
  2. Boa has no JIT. On compute, Boa is far slower than JavaScriptCore. A swap in that direction loses speed.
  3. The child-process agent model costs more per agent than an in-process call. That cost is paid for safety, not for speed. It is a correct trade, and it is not the bottleneck.

The engine is not running while the time passes.

4. What transfers from Hadoop, and what does not

Hadoop was not fast because of its runtime. Its runtime was the JVM, and the JVM was not the reason. Hadoop was fast because it split work into many small tasks, moved the work to the data, ran the tasks wide, re-ran the slow ones, and cut the data volume between stages.

Hadoop techniqueAgent equivalentCurrent state
Partition into many small tasksMany short agents1.22× only
Data localityRoute work to a warm context cacheMissing
Wide fan-outConcurrency limit4 (Claude Code ~10)
Straggler re-executionRestart or split a slow agentMissing
Combiner — less data per stepFewer model round trips per stepThe largest lever

The primitives already exist in crates/workflow/src/prelude.js: mapReduce, shard, partition (FNV-1a), reduceByKey, combine, pipeline, parallel, verify and keepUnrefuted.

The primitives are not the gap. Nobody partitions the work finely enough to use them.

5. Workstream A: cut tool round trips (largest payoff)

Evidence: R² = 0.69 between tool calls and duration, 65 calls per agent, and 16.5 s of agent time per call — derived, not measured (2.4).

A1 — Deterministic tool-result cache keyed by content digest

  • Design. The key is (tool name, normalized argument digest, input content digest). Only read-only tools that are declared deterministic take part. For cargo check -p X the key covers the crate source tree digest, the lockfile digest and the toolchain.
  • Seam. crates/core already computes digests. crates/recorder already records call evidence. Both seams exist.
  • Guard. The key is content, never time, so invariant 4 (pinned byte changes re-gate) holds. Never cache a tool that writes. Never cache across the trust gate, and never cache anything that resolves secrets.
  • Witness. Change one byte in a crate. Prove the key changes and the result is recomputed.
  • Expected payoff. Repeated cargo check and grep inside one run cost about zero. Cargo alone is 23.2 s mean over 132 calls.

A2 — Fewer, richer tools (a combiner tool surface)

  • Design. The model pays 16.5 s per round trip whatever the tool returns. So return more per call. Replace "grep, then read six files, then reason" with one call that answers the question — for example, a symbol together with its definition and its callers.
  • Seam. The tool surface in crates/cli. This does not touch trust or policy.
  • Guard. Invariant 7 — bound the output size, treat all repository content as hostile, and never interpolate content into a shell command. Also invariant 6 — do not create a second dispatch path.
  • Witness. A bounded-output test and a hostile-content test on each new tool.
  • Expected payoff. 65 tool calls per agent down to 40.

A3 — Batch independent tool calls in one turn

  • Design. This is already possible and it is used poorly. Independent calls in the same turn cost one round trip, not many.
  • Seam. Authoring guidance. Near-zero code.
  • Guard. None needed; no new surface.
  • Witness. Count of calls per turn, before and after.
  • Expected payoff. Real, and it is nearly free.

A — the arithmetic

Cutting tool calls from 65 to 40 removes 25 turns. At 16.5 s per turn that is 6.9 minutes off a 17.8 minute agent. That is a 39% reduction for each agent.

Read that 39% as an upper bound. It assumes that removing a tool call removes 16.5 s of wall time. It does not. The 16.5 s is derived (2.4) and contains the real execution time of the work as well as the round trip — cargo alone is 23.2 s mean over 132 calls. That work does not vanish when a tool gets richer; the caller still needs the answer. Only the round trip is removed. A2's true payoff is 25 round trips, plus whatever thinking time those turns carried, and not the compile and read time folded into the same average. A1 is the exception: a cache hit removes the execution too, which is why it is sequenced first.

This is the single largest measured lever in the plan. It also compounds with any parallelism gain from workstream B: a 39% shorter agent and a wider fan-out multiply, they do not merely add.

5b. Why tool calls cost so much

Each tool call costs one full model turn. Each turn re-reads the agent's whole context. This is the mechanism behind the correlation in section 2.

Measure, 86 agent transcriptsValue
Mean turns per agent81
Mean context per turn63,760 tokens
Largest single context209,238 tokens
Prefill amplification269.5× (input tokens processed per output token)

Stated plainly: the agents processed 509.8 M input tokens to produce 1.89 M output tokens. Almost all of that input is the same context, read again on every turn.

This is why tool call count correlates with duration (R² = 0.69) more strongly than token volume does (R² = 0.43). The count of turns sets the number of times the context is re-read.

The cache does not remove this cost. It makes each re-read cheap per token, but it does not make the turn free. The measured 16.5 s per tool call was measured with the prompt cache already running at a 96.7% hit ratio.

6. Workstream B: raise real parallelism

Target: 1.22× to 3×, both as parallelism (busy time ÷ wall time).

State the hard ceiling first — and state which ratio each number is. An earlier version of this section compared 1.22× against 2.06×, which mixed two different ratios. There are two, and they have different denominators:

  • Parallelism = busy ÷ wall. Today: 1016.8 ÷ 832.0 = 1.22×. The target 3× is this ratio.
  • Speedup = today's wall ÷ a hypothetical wall. Under perfect scheduling on the current task shapes, wall time falls to the sum of the per-run longest agents, 404 min, so speedup is 832 ÷ 404 = 2.06×. That is a speedup, not a parallelism, and it is not comparable to 1.22×.

Expressed as parallelism, the perfect-scheduling ceiling is 1016.8 ÷ 404 = 2.52× — not 2.06×. So the honest chain, in one consistent ratio, is: parallelism 1.22× today → at most 2.52× with perfect scheduling on today's task shapes → target 3×. Note that this makes the target strictly above the scheduling ceiling: 3× is not reachable by scheduling at all. It requires finer partitions (B2), which change the task shapes and so move the 404 min bound itself. B1 and B3 can only close the 1.22× → 2.52× part.

B1 — Raise DEFAULT_MAX_CONCURRENT from 4

  • Seam. crates/cli/src/commands/workflow.rs:67. Machine policy can override it at :553-557.
  • Guard. Invariant 2 — the machine ceiling sets the maximum, and a project may only narrow it.
  • Risk. More child processes means more memory and more API rate pressure.
  • Proposal. A measured ramp, 4 to 8, with a witness that the worker pool joins cleanly on every exit path (PoolGuard, :1459-1473).
  • Prerequisite — do not skip this. The 1.22× that motivates B1 was measured on Claude Code, not on AgentStack's runner (2.6). AgentStack spawns a child process per agent and Claude Code does not, so the right concurrency for AgentStack may be lower than 4, not higher. Measure AgentStack's own parallelism and per-agent cost under its own load first. B1 is the one item in this plan whose evidence does not transfer.

B2 — Finer partitioning: make small tasks the easy path

  • This is the real blocker. Three to seven agents of 17.8 min each is a coarse partition.
  • No engine change is needed.
  • Design. Add an explicit enumerate-then-fan-out step. It is the equivalent of a Hadoop input split: a cheap agent lists the work units, then the script maps over them.
  • Seam. A prelude helper, so this shape becomes the default shape.
  • Acceptance. Median agent duration below 8 min, and more than 15 agents per run.

B2 pays twice, not once. A shorter agent accumulates a smaller context, so every turn inside it re-reads less. The mean context per turn is 63,760 tokens and the worst case is 209,238 tokens, so a long agent pays far more on each turn than a short one does. Finer partitions therefore raise parallelism and lower the cost of each turn.

B3 — Confirm continuous dispatch is really used

  • Design. StepOutcome::Awaiting (crates/workflow/src/lib.rs:277-285) exists so the host can step as soon as any one child finishes, instead of joining a batch.
  • Action. Verify the CLI dispatcher does this. If it joins the batch, fix it.
  • Effect. This removes straggler waiting inside a stage.
  • Cost. A cheap correctness check. Do it early.

7. Workstream C: straggler control

Evidence: the slowest agent runs 59 min against a 17.8 min mean. That is 3.3×.

C1 — Progress-based stall detection

  • Design. lastProgressAt is already recorded for each agent. Add a rule in dispatch_worker (crates/cli/src/commands/workflow.rs:1479): flag an agent that passes K× the phase median and has made no tool call for T seconds.
  • Guard. Detection only. It changes no authority.

C2 — Bounded speculative re-execution

  • Design. Hadoop's technique, transferred directly. Re-issue the task once with a different decomposition hint, take the first result, and kill the loser with the existing tree-kill (ChildPids, crates/cli/src/runs.rs:529).
  • Cost guard. At most one speculative copy, only past the threshold, and only when a worker slot is free. Speculation raises the token cost for that task.
  • Guard. Invariant 1 — no new unsafe code. Process management stays inside the existing crates/cli/src/sys.rs boundary.
  • Blocking guard — side effects. See below. C2 is not safe without it.

Hadoop's speculation is safe for a reason C2 does not inherit: its tasks are idempotent and write nothing outside a staging area until commit. Killing a Hadoop task loser discards a staged directory. Agents write files directly. A killed agent leaves whatever it had already written — partial edits, half-applied refactors, files that compile but were never verified.

This is not hypothetical. It happened twice during the delivery work: one agent died mid-task leaving 423 compiling but unverified lines; another left 136 lines across three files. In both cases the tree looked healthy and the build passed — which is exactly what makes it dangerous, because the usual signal that something is wrong did not fire. C2 proposes to produce that same state deliberately, once per speculative task.

The constraint: the loser's writes must be isolated, not merely stopped. The workable form is a git worktree per speculative copy — each copy writes into its own tree, the winner's tree is merged or promoted, and the loser's tree is discarded whole. Any design where two copies write into the same working tree is unsafe regardless of how fast the kill is, because the kill lands mid-write by construction. Until that isolation is designed and witnessed, C2 does not start. This constraint applies to C2 alone; C1 is detection only and is unaffected.

Note the advantage. Here the child-process model is strictly better than an in-process model, because a straggler can really be killed — but killing cleanly is a necessary condition, not a sufficient one.

8. Workstream D: cache-affinity routing — measured and rejected

D was the data-locality transfer: record what each agent reads, then order and group tasks so that consecutive tasks share a context prefix and keep the provider-side prompt cache warm.

D0 was run before any code was written. The measurement covers all 86 workflow agent transcripts and 6,997 assistant turns. It reads cache_read_input_tokens and cache_creation_input_tokens from message.usage.

Uncached input84,1110.02%

The prompt cache hit ratio is already 96.7%. The remaining headroom is 3.3%. That 3.3% is cache-write and uncached traffic, and no routing scheme can remove all of it. D would build a task-ordering system, a per-agent read-set record and a routing rule to chase a fraction of 3.3%.

D is dropped in full. D0 is complete, D1 and D2 are cancelled, and nothing in D needs a decision.

The process point matters more than the result. D0 cost a few minutes and removed a whole workstream. It needed no new code, no new dependency and no design. Gate every speculative workstream behind a cheap measurement of the prize, and run that measurement first.

9. Sequencing

D is not in this list. D0 is done and D1 and D2 are cancelled (section 8).

  1. B3 — cheap correctness check; do it before anything depends on dispatch behaviour.
  2. A1 + A3 — largest payoff at the lowest risk.
  3. B1 — small change, but it needs a witness.
  4. B2 — the real win, and mostly authoring guidance.
  5. A2 — medium effort, so it comes after the cheap items.
  6. C — after B, because straggler thresholds need a stable phase median.

10. Ceilings and honest limits

  • Perfect scheduling on the current task shapes gives at most 2.52× parallelism (busy ÷ wall), which is the same thing as a 2.06× speedup against today's wall time. The longest agent in each run sets the floor on that run's wall time. Do not compare the 2.06× against the 1.22×: they are different ratios (section 6).
  • A realistic target with finer partitions and 8-way concurrency is about 3× parallelism. It is not 10×. It is above the scheduling ceiling, so it depends on B2 changing the task shapes, not on B1 or B3.
  • Amdahl's law. If 30% of a workflow is serial — the synthesis and verify stages — then the maximum speedup is 3.3×. The review workflows have exactly this shape.
  • Parallelism buys latency, not efficiency. Sixteen agents in parallel use sixteen times the tokens per minute. Speculation raises the cost further. Hadoop had the same property.
  • API rate limits bound the fan-out independently of the machine.

12. Explicitly not in this plan

  • Replacing Boa with a JIT engine. The measured contribution is about zero. Boa's sandbox posture is the point of the choice. A JIT host would need the filesystem, network and process capabilities that the posture forbids.
  • A second user interface. The old embedded dashboard stays removed.
  • Any capability lane outside STRATEGY.md v3's shape without maintainer adoption.

13. Decision required

Three options:

  1. Adopt the whole plan as a new lane.
  2. Adopt only the cheap subset that is arguably maintenance — A1, A3 and B3 — and defer the rest. D0 is already done, so it needs no decision.
  3. Shelve the plan.

No work starts and TODO.md is not edited until the maintainer chooses.
