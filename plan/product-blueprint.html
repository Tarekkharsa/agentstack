What blocks what
One manifest for your whole agent setup, delivered to every coding CLI — and a runtime plane that governs what agents are allowed to run. In plainer words: you write your agent setup down once, it reaches every coding tool on your machine, and a second layer decides what those tools are actually allowed to do.

Start here

Four panels, about five minutes. Everything below them is reference.
1What this isTwo halves, one bet

Half one: you describe your agent setup once — servers, skills, instructions, settings — and the tool delivers it to every coding CLI you use, so you stop maintaining the same thing three times.

Half two, and the real bet: a layer that decides what those agents are allowed to run, reach and read. The first half can be copied. The second is much harder to.

AREA 1

Your setup, and how it travels

The part a new user meets first. You describe your agent setup once, and it reaches every coding CLI on the machine — with the bytes fingerprinted, so what you approved is what runs.

One folder holds it all

Servers, skills, instructions, hooks and settings live in one place, and every file is fingerprinted.
Shipped Everything you set up lives in one folder crates/core

The .agentstack/ folder is the setup file your project keeps — MCP servers, skills, instructions, hooks and settings as one declared thing. There is no second place to look.

Every file gets a fingerprint, and a lockfile records what was resolved. That is what makes a setup reproducible, and what makes drift visible instead of silent.

Two ways to reach a CLI

Served live where the tool can take a connection; written into its own config files only where it cannot.
Shipped Reach every CLI without writing files where you do not have to crates/cli

The live lane. The setup is served to the coding tool over a connection, and no project files are written at all. This is the default wherever the tool can take one.

The written lane. Whatever a live connection cannot carry is compiled into the tool's own config — inside a marked region of files like CLAUDE.md and AGENTS.md, so the region is owned and can be taken back out.

The CLIs it knows about

Thirteen of them, described as data — and the documentation is careful about which ones are actually checked.
Shipped Thirteen coding CLIs, and an honest word for each crates/adapters

Each CLI is described in a small data file rather than hand-written code: Claude Code, Claude Desktop, Codex, Cursor, Windsurf, Gemini, Copilot CLI, VS Code, opencode, Kiro, Junie, Antigravity and pi. Adding a CLI is data, not a new code path.

It reads the setup you already have instead of asking you to type it in again.

That is the whole first-run promise: you do not re-type a setup you already have.

AREA 2 · THE HARD-TO-COPY PART

Keeping agents inside the lines

Not a list of features — one path with a gate on it. Content from a repository can do nothing until a person reads it and approves those exact bytes, and every call afterwards goes through a single door that checks the approval again.
the files→ you approve them→ rules narrow them→ one door→ network proxy→ recorded

One deliberate yes

You approve what you read. Change one byte and you are asked again.
Shipped One deliberate yes, tied to the exact bytes you saw crates/trust

Approval is bound to the content it was given for. Change a byte and the approval is gone — the gate runs again. There is no cache and no half-approved state that would loosen that binding.

  • One deliberate yes, after the full content has been shown to you.
  • The prompt refuses piped input, so an agent cannot answer it on your behalf.
  • What gets fingerprinted is what gets read — there is no window in between.
Hooks count as executable. A hook runs commands with your permissions, exactly as an extension does. So the full approval ceremony always applies to hooks, and no shortened-consent path may ever cover them.

Rules tighten, never loosen

A project can be stricter than the machine allows. It can never be looser.
Shipped A project can tighten the rules; it can never loosen them crates/policy

What actually applies is the overlap between the machine's widest allowance and the project's own rules. A project can narrow that. A project cannot widen it — not because someone remembers to check, but because an overlap cannot be bigger than either side of it.

This decision lives in its own small piece of code, with no file access and no hidden state, so it can be tested on its own and reviewed quickly.

feedsThe one door feedsRun tiers

One door for every call

There is one code path a call can take, and it re-reads your approval from disk each time.
Shipped Every call goes through one door, checked every time

Every brokered call passes one gateway. There is no second way to be granted permission and no second way out to the network — and that single path is the only reason the safety claims can be checked at all.

Approval is re-read from disk on every call, not remembered from start-up, and the connection out is private, so nothing can reach around the check.

Where traffic may go

Network access runs through a proxy that blocks internal addresses and lying handshakes — with one known hole.
Shipped Network reach is a decision, not a default crates/egress

A proxy sits on the network path. It blocks requests aimed at internal addresses, and it checks that a connection claiming one destination really goes there — so a request cannot name a harmless host and connect somewhere else.

Where this stops. An allowed destination can still be used to leak data. The proxy narrows where traffic may go. It does not judge what is inside it.
Planned Fix the network check that fails open on a malformed handshake F1

One specific malformed shape — a single trailing byte in the connection's destination field — slips past the check instead of being rejected. It is written down rather than quietly carried, and it is first in the queue.

Running things in a box

Runs happen in a container, and each mode prints what it does not cover.
Shipped Runs happen in a box, and the box says what it does not cover crates/runtime

Runs happen in tiers, backed by Docker. Each mode prints a line saying what it does and what it leaves open, so you learn the limit by reading the output instead of inferring safety from silence.

The sharpest limit in the product. Only the sandboxed mode is enforced. Running on your own host is cooperative: the checks there are advice, and advice is not confinement. The word “enforced” belongs to sandbox mode and nowhere else.

What happened, recorded

Calls and runs leave evidence — which answers questions, but stops nothing.
Shipped Every brokered call leaves a record crates/recorder

Every brokered call and every run leaves evidence behind. That is what turns “what did the agent actually do” from a guess into a question with an answer.

Where this stops. Recording is not prevention. The record tells you what happened. The approval step, the rules and the box are what stop things happening.
feedsThe execution idea

Passwords stay out

Your setup holds a name that points at a secret, never the secret itself.
Shipped Passwords are never written into your setup

Configuration holds a named reference like ${REF}; the real value is looked up only when it is needed. If the lookup fails, the command fails — it never quietly substitutes an empty string, so a missing secret is an error rather than a silent downgrade.

Nothing is looked up before you have approved the content, so unapproved files cannot pull a secret into view.

Eighteen tests that try to break the safety promises, each with a control proving the attack was real.
Shipped Eighteen tests that attack the safety claims crates/cli/tests

Each safety claim has a test that attacks it, and each attack has a control — so a test that passes only because the attack was built wrong gets caught.

Nothing changes until you say so

Commands show the change and stop. One flag, everywhere, commits it.
Shipped Nothing changes until you say write

A command that would change something shows you the change and does nothing. --write is the single, uniform way to commit it. Because the rule is the same everywhere, you learn it once instead of per command.

When something is wrong

Four commands for diagnosing, reversing, explaining and finding.
Shipped Four commands for when something is wrong or unclear
doctorEvery finding names the next step on the line below it — 102 such hints in the doctor code alone, 173 across the workspace. A finding that cannot name a fix should not print.
undoThe counterweight to --write. What the tool wrote, the tool can take back.

Talking to a companion app

A graphical companion may read freely and act only in named ways — and one document about it is wrong.
Shipped A companion app can read, but only act in ways the contract names ui_contract.rs

An app asks the binary what it can do — a version number plus a list of 43 named capabilities — instead of guessing from a release number. Retired names are kept and marked rather than silently dropped, so an older app degrades instead of breaking.

The list of actions is closed. There is no general “run this command” escape hatch. An app can only do things the contract names, which is what keeps the companion a companion and never a place where safety decisions are made.

A standing constraint. The command line is the product and the source of authority. The old built-in dashboard stays removed; there is never a second interface.

The parts built on top

Scripted work

A small JavaScript engine with its escape hatches switched off.
Shipped Run scripted work in a caged JavaScript engine crates/workflow

Workflows run inside an embedded engine with the ways out deliberately closed: it cannot load other files, it cannot build and run code from a string, and time and memory are bounded. The dependency stays inside this one part of the codebase.

Each role in a workflow carries its own model and effort setting, and work is dispatched continuously rather than turn by turn.

A named leftover. The pattern-matching engine can be made to take exponential time on a hostile pattern. It is written down rather than papered over.

AREA 6

The direction being adopted

Drafted and argued; it becomes the strategy when the maintainer says so (that choice sits in area 5). The shape of the bet: stop trying to be a package manager, let other catalogues supply the parts, and lead with the half nobody else has.

What we will not build

Four package-manager features, given up deliberately rather than missed.
Decision Four things this product will not build
  • Working out a package's dependencies, and their dependencies.
  • Version ranges.
  • Update and out-of-date checking.
  • A race to own the registry everyone publishes to.

Each of those is a real product with a real team behind it. Competing there spends the entire budget on the half of the problem somebody else already solved.

Where the parts come from

Other people's catalogues become the supply; this product governs the door.
Decision Let other catalogues supply the parts; govern them at the door

APM's ecosystem, vercel skills and the public MCP registry become supply that enters through the approval step. You do not have to own the shelf to govern what comes off it.

A smarter way to run work

The agent says what it intends; the tool plans how to do it. Four corrections already made to the sketch.
Idea Let the agent say what it intends, and plan the run for it

The proposal turns the usual arrangement around: the agent states what it means to do and how sure it is, and the tool works out how to run it. It would sit on parts that already exist — the record, the fingerprints, the single door.

Four corrections were made before it was written down:

  • When unsure whether a cached result still applies, redo the work — a wrong cache hit is worse than a slow one.
  • Let build tools do their own incremental work instead of modelling it here.
  • Give parallel writers separate checkouts.
  • Use the existing record as the one memory, not a second store.

Only two small pieces are seeded: caching a tool result against its fingerprint, and batching calls that do not depend on each other — and even those wait on the work queue being reconciled. The rest is trigger-gated.

AREA 8

Rules that do not move

These hold across every area above. They are not goals to aim at — they are properties any change has to leave intact.

The eight rules

Properties every change has to preserve, in plain terms.
Shipped Eight properties every change has to preserve
1 · No new memory-unsafe codeEvery part of the codebase forbids it, except one existing, concentrated place that starts processes.
2 · Rules only narrowWhat a project ends up with is always inside what the machine allows.
3 · Unapproved content can do nothingIt cannot start or contact servers, reach the agent, or look up a secret before you approve it.
4 · Changed bytes mean asking againNo cache and no half-approved state may weaken that.
5 · Secrets are never written downConfiguration holds a reference; an unresolved one fails rather than defaults.
6 · One way to be granted, one way outNo second permission path; no second connection to the outside.
7 · Treat every repository file as hostileParse it carefully, bound it, and never paste it into a shell command.
8 · Claims match what the code enforcesThe register below is this rule in daily practice.

Where the words stop

Four sentences that keep the claims from growing past the code.
Shipped Four sentences that stop the claims growing
Advice is not confinementOnly the sandboxed mode is enforced. Host mode is cooperative, and says so.
Recording is not preventionThe record is evidence. The approval, the rules and the box are the stops.
An allowed destination can still leakThe proxy narrows where traffic goes, not what it carries.
Best-effort is not “supported”Eight of the thirteen CLIs are not checked nightly, and the docs refuse the word on purpose.
Why this is a feature. A tool that tells you its limits is a tool you can reason with. Every softened claim buys the credibility of the claims that are not softened.
