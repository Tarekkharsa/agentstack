### F3 — `doctor-probe-v1` missing from T3

Status: **FIXED**

The completed path includes:

- probe result schemas;
- `agentstack.doctorProbe` RPC;
- server invocation of `doctor --probe --json`;
- workspace-root resolution;
- `agentstack:admin` authorization;
- a positive `doctor-probe-v1` UI gate;
- explicit confirmation that every declared stdio server will be started;
- structured per-server results;
- first-class handling of `ran: false`;
- trust-review routing for untrusted/drifted projects, with no pointless retry;
- focused logic, render, bridge, and authorization tests.

The real browser showed **Test server startup**, the side-effect explanation,
and the drift refusal. The refusal offered **Review this project**, did not
offer a retry, and opened the trust review. When the feature name was withheld
while the payload still carried a `probe` field, the startup control disappeared.

### F4 — `workflow-serial-roles-v1` dropped

Status: **FIXED**

The workflow schema now carries optional `serial_roles`, and the panel gates
the warning on the workflow read's own `workflow-serial-roles-v1` envelope.
For the regression fixture:

```json
{
  "roles": ["builder"],
  "serial_roles": ["builder"],
  "max_agents": 4
}
```

T3 now renders both the true ceiling:

> builder · ≤4 agents

and the missing scheduling fact:

> builder runs one child at a time — that harness takes no per-child MCP
> config, so the ≤4 ceiling doesn't apply to it.

When the feature name was withheld while `serial_roles` remained in the
payload, the warning stayed hidden. This proves the UI negotiates the contract
rather than sniffing an optional field from a newer CLI.
