The complete journey, in order

Every feature as a moment, from install to scale

The full product told as one chronological journey — twelve moments in four stages. The six defining moments from STRATEGY.md are here (tagged with their phases); the rest already ship and show where today's features sit in the same story.

Delivery ambition: dynamic as the eventual default. At the end state the spine is zero-files mode — the gateway registers once per CLI, capabilities lease in per project and per task, and skills load on demand: a name+description index sits in context, the body arrives only on load. Every dynamic load passes the gateway, so policy and audit stay on the path — the property no convention-only system can claim. Honesty note: the shipped default is static and stays so until three named preconditions are met (the zero-files consent question resolved, an honest ENFORCEMENT column for the lease path, first-run friction measured acceptable) — evaluated at the Phase 3 gate, flipped no earlier than Phase 4. Static render and sessions remain permanently for what MCP cannot inject (native instruction files, extensions, offline starts).

Stage 2 · Work — the daily loop

Moment 3 · Skills load themselves today

Inside the session: index in context, body on demand

The agent sees a small index of what's loadable. When the task needs a skill, it loads it — one brokered, recorded, policy-checked call. Context stays small; nothing touches disk.

claude — inside the trusted project

› tool agentstack_list_loadable("pdf")
    summarize-pdf   Extract & summarize PDF content · library
› tool agentstack_load("summarize-pdf", reason: "digest quarterly report")
    ← skill body loaded into context · nothing written to disk
· gateway: call brokered · policy checked · recorded → run 0147
Moment 4 · Write a skill P1

Drop a file. Say yes once. Live everywhere.

The user creates skills/summarize/SKILL.md in their project — nothing else. The next time any AgentStack touchpoint runs, the file has been noticed, pinned, and staged. The manifest and lock update themselves; the user never opens them. Provenance gates the compression: this one-yes path applies only to content with a local-authorship signal (untracked in git, or newer than the last trust grant) — anything that arrived with a clone takes Moment 6's full staged review instead.

How the panel integrates — actions recipe vs. plugin

TierWhat it isStatusBest for
1 · Project-actions recipe Stock t3code's built-in custom actions running agentstack commands (the docs/integrations.md recipe) — buttons, output in the terminal, zero UI code Ships today Anyone on stock t3code; study participants; any other editor with runnable tasks
2 · The fork panel The full panel in the t3code fork: MCP read APIs + shim run tracking + the fixed digest-bound action set — everything wireframed above Ships today (fork) The best experience; the reference implementation of the contract
3 · A distributable plugin The same panel packaged for an upstream extension API (t3code's if one stabilizes, or VS Code's) — a thin renderer over the identical contract Deliberately deferred Only when a publicly obtainable host + real users exist (post-§1.6 evidence)

The decision rule: the integration contract is the product; every UI is a thin renderer over it. The MCP read APIs, the shim, and the epoch-versioned fixed-action set are what get engineering investment — they make tier 1 work today, power tier 2, and make tier 3 cheap if it ever earns its place. Building a plugin now would mean betting on an extension API of a host that has no public download yet, for users who don't exist yet — both named blockers in STRATEGY.md. Neither-nor is also wrong: relying only on tier 1 would cap the experience at buttons-and-terminal. Keep both shipping tiers, defer the third, and let the v2 additions land as a handful of new read APIs and fixed actions: intake list, review-card data, digest-bound approve, undo timeline, dynamic-load events.

Architecture at the end state

Same spine, new front door

v2 adds no new crates and no second authority path. Everything lands along the existing seams: the funnel is a new front door into the same resolve → lock → trust → render spine, and the yes is a better face on the trust gate that already exists. The one structural addition is intake — a staging state for content that has arrived but has not been consented to.

On-disk structure at the end state

Three places, each with one job

my-project/
└─ .agentstack/
   ├─ agentstack.toml        system-written · review in PRs
   ├─ agentstack.local.toml  personal overlay · gitignored
   ├─ agentstack.lock        SHA-256 pins · the consent surface
   ├─ skills/                drop a folder here → staged (P1)
   ├─ instructions/          drop a file here → staged (P1)
   └─ extensions/            executable · full ceremony, always
~/.agentstack/
├─ agentstack.toml   machine manifest · policy ceilings · guard
├─ trust store       path-keyed consent + timestamps
│  └─ recognition    content-addressed approvals (P2)
├─ adapters/         your drop-in descriptors (trusted: you put them there)
├─ library/          central capabilities: skills · servers · extensions · hooks
│  └─ .trash/        removals are restorable, never deleted
└─ runs/             flight-recorder evidence · workflow trees
what the harnesses see  (rendered output, never the source of truth)
.mcp.json · .claude/skills/ · CLAUDE.md/AGENTS.md managed regions · Codex config.toml · …
   static mode: on disk, gitignored via managed block · clean-at-rest: only during a session
   zero-files: nothing on disk — capabilities arrive through the gateway lease

The reading order for a human is deliberate: the project tree is what you review in a PR, the machine tree is what only you control (no repo content can reach it), and the rendered layer is disposable output that status can always regenerate or undo can always retract.

Two authoring scopes, one resolution path. A capability can live in the central library (~/.agentstack/library/) — reusable across every project, and syncable as your own git repo via lib sync (commit, pull, push; secrets never travel because server definitions carry ${REF} only) — or at project scope (.agentstack/), where it travels with the repo and is exactly what the trust gate reviews when someone else clones it. Project manifests reference library entries by name; lock resolves both to pinned content the same way, so scope changes where a capability lives, never how it is verified.

Net change to the surface: four new verbs (yes, up, undo, share), each a composition of primitives that already exist and remain scriptable underneath. Nothing is removed; several things stop being something the user must remember.

The end state, enumerated

Every feature of the finished product

Grouped by the four ideas the user actually holds, plus the yes. P0–P4 tags mark which phase of STRATEGY.md delivers each; unmarked items already exist today and carry forward.

Setup

What do I have?

  • Auto-detect & import every installed CLI's existing config into one environment
  • One-command bootstrap on any machine — agentstack up P4
  • Self-writing manifest & lock — system-authored, human-reviewed P1
  • Machine vault — secrets as ${REF}, resolved locally, never serialized
  • Adapters for 13+ harnesses, data-driven, one render path

Toolset

What does this task use?

  • Named toolsets spanning skills, servers, instructions, hooks
  • Instant switching — feels like changing terminals, per project or per task
  • Three delivery modes, chosen for you by default: static, clean-at-rest, zero-files
  • Drop-a-file authoring — new capability from a file in the tree P1
  • One shape for every kind — learn one capability, know them all P3
  • Central library — reuse across projects without copy-paste

Status

Is it ready?

  • One-line answer with exactly one next action, never a bare finding list P3
  • Drift explained in plain words — what changed, keep it or fix it
  • Seatbelt legibility — every denial: one sentence + evidence + safe next step P3
  • Run reports — what ran, what it touched, what was refused, per run
  • CI mode — the same checks, non-interactive, reproducible

Undo

How do I take it back?

  • Undo named in the same breath as every material change P2
  • Timeline recovery — pick the moment, one keystroke back P3
  • Ownership-aware — only what AgentStack placed is ever pruned
  • Undoable undo — recovery is never a cliff

The yes

Do I accept this exact content, here?

  • Staged intake — everything arrives inert: dropped files, cloned repos, registries P1
  • The review card — 2–5 plain lines: runs, contacts, reads, changed P2
  • Byte-exact re-gating with a real diff, not "digest mismatch" P2
  • Recognition — same bytes shorten the card, never skip it P2
  • Sharing is signing, receiving is reviewing P4
  • Governed intake from any ecosystem — including ungated ones P4

Underneath (opt-in depth)

More protection, when you ask for it

  • Policy ceilings — machine ∩ project, deny wins, rename-proof
  • Sandbox & lockdown — topological confinement, enforced egress
  • Single gateway authority — every brokered call through one policy check
  • Flight recorder — append-only evidence for every governed run
  • Governed workflows — the advanced lane, gated on its own review
