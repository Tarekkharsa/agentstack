One agent setup. Every coding CLI.

AgentStack collects the MCP servers, skills and instructions you already use into one .agentstack/ directory, then serves them live to your coding CLIs — so the project stays clean. What no live channel can carry, and every tool without MCP, is written into native files instead. Named toolsets switch by project or task, and every change stays understandable and recoverable.

the gaps it closes

Your tools should share one setup

AgentStack manages the complete lifecycle: import, activate, switch, diagnose, recover and share — with safety built underneath.

Every CLI spells setup differently

Import your existing configuration once. AgentStack then routes it per tool: served live over one gateway where the tool speaks MCP, written in the correct native format where it does not.

Switching tasks pollutes shared files

A toolset selects the servers and skills one task needs. Temporary sessions activate it and restore the previous native configuration afterward.

Native configuration drifts

Doctor finds the problem, diff shows what would change, adopt keeps an intentional hand edit, and restore undoes a bad write.

Portable must not mean automatic

Unfamiliar repository configuration stays inert until reviewed. Any pinned change re-gates it, and machine policy always remains the ceiling.

quick start

Five minutes to first value

Four commands, then plain files you can open, read and commit. The third is not optional: until the bridge is registered, nothing routed live reaches your tools.

Prefer guided? Take the tutorial →
bash
$curl -fsSL https://raw.githubusercontent.com/Tarekkharsa/agentstack/main/install.sh | sh
$agentstack init# guided wizard: your CLI configs → one manifest
$agentstack x gateway connect --all --write# register the bridge, once, so live delivery reaches your CLIs
$agentstack status# is it ready — and the one thing that fixes it
your-project/
your-project/ ├── .agentstack/ │ ├── agentstack.toml # everything your tools may run: servers, skills, instructions │ ├── agentstack.lock # the pins — exact commits and content digests │ └── .env # token values lifted out of your configs (only when init found any) └── .gitignore # two managed lines: a comment, and /.agentstack/.env
  • Guided wizard: your CLI configs → one manifest.
  • Status says whether it is ready — and the one thing that fixes it.
  • What it leaves behind is plain files you can open, read and commit.

The install line above gives you v0.17.1 — that is the current stable release, and what /releases/latest resolves to. agentstack yes, undo, up, share and receive — and every transcript further down this page — are v0.18.0-rc.2, a prerelease curl will not hand you unless you name it: AGENTSTACK_VERSION=v0.18.0-rc.2. agentstack --version says which you have.

.agentstack/agentstack.toml records your whole setup — the manifest. Every CLI-specific file AgentStack writes is rendered from it, and can be regenerated or taken back off at any time. Mostly the system writes it for you — and when you write a skill of your own you don't open it at all: drop the folder under .agentstack/skills/, run agentstack yes, review once, and it is live in every CLI. After an import its [servers] block is empty: the server definitions land in your library and the manifest references them by name. The ${GITHUB_TOKEN}-style placeholder lives in that library definition — ~/.agentstack/lib/servers/github.toml — and neither file ever holds the token value.

That is the run replayed at the top of this page. Reproduce it fenced with examples/first-value-demo/run-demo.sh — it asserts every step, so the recording stays accurate.

the everyday loop · one deliberate yes

What using it feels like

Four moments, captured from v0.18.0-rc.2 exactly as it prints them — a capture, not a mockup. Where a transcript is longer than its pane it is cut at a …, and absolute temp paths are shortened to ~/your-project; no line is reworded. v0.18.0-rc.2 is a prerelease — the install line above serves v0.17.1, which has none of these commands. Everything is automated except the one thing that never is: your yes.

$ agentstack yes → 1 dropped file ready to go live in this project: + skill summarize (./skills/summarize) Summarize a document into a short brief. your own work — untracked in git ✓ pinned 1 skill + 2 servers This will write: Claude Code · MCP servers are served live, not written — nothing for `use` to render here ✓ skills up to date Codex CLI · MCP servers are served live, not written — nothing for `use` to render here ✓ skills up to date … Make this live? [y/N]

Write a skill: drop the folder, say yes. No manifest edit — it is pinned, recorded, and live in every CLI. Nothing is written into the project for it: on an MCP-capable tool the skill is served live. The short review is only for what git says is yours — the project is a git repo and the file is untracked. Outside a repo, or for anything that arrived with a clone, yes refuses the short path and sends you through the full staged review. Add a skill →

$ agentstack undo recent changes (newest first) 1 just now init 7 files · Claude Code, Codex CLI pick a point: agentstack undo --to <n> --write

Take it back, from a timeline. Every write is recorded before it lands; pick a point and revert to it. The revert is recorded too — going one step too far is recoverable. Undo anything →

$ agentstack guard test "printf 'K=1' > .env" DENY printf 'K=1' > .env blocked: a write to .env was refused — denied by [policy.filesystem] deny rule "!.env" (machine policy — ~/.agentstack/agentstack.toml) nothing was written · edit that [policy.filesystem] rule if this path should be allowed …

The seatbelt speaks plainly. A refusal says what was stopped, why, that nothing happened, and the one safe next step. This one is the machine-policy guard turning down a write to a secret file — cooperative accident protection, wired into every detected CLI as a pre-tool-use hook. Kernel-enforced confinement is a different lane, agentstack run --sandbox; both are mapped on the paths where enforcement really runs.

$ agentstack share backend signing as 728a-16ee-41b1-f18a ✓ bundle backend.astack (manifest + lock + 1 pinned file) $ agentstack receive backend.astack Review — a shared bundle signed by 6197-28b5-1e88-ffa5 — a publisher you have not recognized before. … Adds 1 skill file The bundle's manifest and lockfile are used to verify these files, not merged — servers, toolsets, and policy do not cross over staged at ~/your-project/.agentstack/quarantine/c362115b… · nothing is active

Sharing is signing; receiving is reviewing. Only skill and instruction files cross over. The bundle's manifest and lockfile come along to verify those files, not to be merged — the sender's servers, toolsets and policy stay behind.
